# adopt 3단계: tasks

adopt의 tasks는 **도입 작업**입니다. 코드 동작을 바꾸는 태스크는 없습니다.

## 읽을 것

1. `<BASE>/../../rules/adopt.md`의 "3단계: tasks"
2. `<BASE>/../../rules/feature/tasks-format.md` — 줄 형식, 참조, Dependency Graph
3. `<BASE>/../../templates/adopt/tasks.md` — 도입 작업 골격

## 절차

1. **단계 잠금을 확인합니다.** `SM gate <기능> tasks`가 실패하면 멈추고 상태를 알립니다.

2. **입력을 모읍니다.**
   - requirements의 모든 기준
   - design 05의 기존 테스트 이관 표와, 테스트가 없는 기준
   - design 02의 `기준 ↔ 코드 분기` 표 (주석을 달 위치)

3. **작성합니다.** `SM scaffold <기능> tasks`로 골격을 만듭니다. adopt 명세에는 도입 작업 템플릿이 쓰입니다.
   - 1번: 테스트 지원 코드 확인
   - Requirement마다 상위 태스크 하나, 하위 태스크로
     - `기존 테스트 정리: <테스트 묶음>`
     - `빠진 인수 테스트 추가` (테스트가 없는 기준만. 없으면 이 하위 태스크를 뺍니다)
     - `코드 주석`
   - 마지막: `최종 Checkpoint - 명세 동기화`
   - 모든 기준이 어떤 태스크의 `_Requirements_`에 있어야 합니다.
   - Property 테스트는 선택(`*`) 태스크로 그 Requirement 묶음 안에 둡니다. **지금 코드에서 통과해야** 하는 테스트입니다.
   - Overview에 "코드의 동작은 바꾸지 않는다"와 "새 인수 테스트가 실패하면 멈춘다"를 씁니다.

4. **기계 검사를 통과시킵니다.** `SM check <기능>`의 **오류를 0건**으로 만듭니다.

5. **독립 리뷰를 받습니다.** `<BASE>/../../rules/workflow.md`의 "리뷰"를 따릅니다. 단계는 `adopt-tasks`입니다. 코드 동작을 바꾸는 태스크가 섞이지 않았는지 확인하게 합니다.

## 보고

- Requirement별: 정리할 기존 테스트 수, 추가할 테스트 수, 주석 달 분기 수
- 리뷰 결과 표 (지적 / 처리 / 이유)
- 승인 뒤 할 일: `/spec-mirror:implement <기능>` (adopt 명세는 새 테스트가 **바로 통과**해야 합니다)

## 하지 않는 것

- 코드 동작을 바꾸는 태스크를 넣지 않습니다. bugfix 후보는 태스크가 아니라 보고에 넣습니다.
