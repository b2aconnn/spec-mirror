# adopt 2단계: design

일반 기능 명세의 design 안내를 따르되, **새로 설계하지 않고 지금 구조를 설명**한다는 점이 다릅니다.

## 읽을 것

1. `<BASE>/../spec/stages/design.md` — 일반 기능 명세 design 안내. 아래 "다른 점" 외에는 그대로 따릅니다
2. `<BASE>/../../rules/adopt.md`의 "2단계: design"
3. `<BASE>/../../rules/feature/design-format.md`

## 다른 점

1. **지금 구조를 설명합니다.** "추가한다", "새로 만든다", `(변경)`을 쓰지 않습니다. Overview 첫 문장은 "본 문서는 <시스템>의 **<기능>**을 코드 그대로 옮긴 기술 설계입니다."처럼 씁니다. 설계 목표는 "지금 코드가 지키고 있는 원칙"입니다.
2. **코드에서 가져옵니다.** 컴포넌트, 엔티티, DTO, 에러 코드, 설정, DDL은 실제 코드와 설정 파일에서 옮깁니다. 지어내지 않습니다. 길면 핵심만 보여 주고 파일 위치를 적습니다.
3. **02 끝에 `### 기준 ↔ 코드 분기` 표**를 둡니다. requirements 단계의 대조표에 코드 위치(클래스 · 메서드)를 붙인 것입니다. 모든 기준이 표에 있어야 합니다.
4. **05에 기존 테스트 이관 표**를 둡니다. `<기존 테스트 이름> → R{N}-{M}`. 어느 기준에도 해당하지 않는 기존 테스트(기술 단위 테스트 등)는 "이름 유지"로 적습니다.
5. **07의 Property는 지금 코드가 지키는 성질만** 씁니다. 지키지 않는 성질을 찾으면 Property로 쓰지 않고 bugfix 후보로 보고합니다.
6. **08은 지금 설정**입니다. 바뀌는 것이 없으면 "변경 없음 — 기존 설정 그대로"라고 씁니다.
7. **리뷰 단계 이름은 `adopt-design`**입니다. 리뷰어에게 관련 코드 경로를 넣고, design의 코드 조각과 표가 실제 코드와 같은지 확인하게 합니다.

## 보고

일반 안내의 보고 항목에 다음을 더합니다.

- 기존 테스트 이관 표 요약 (이관 / 이름 유지 / 테스트 없는 기준 수)
- design을 쓰며 새로 찾은 bugfix 후보
