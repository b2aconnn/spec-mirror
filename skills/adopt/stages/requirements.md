# adopt 1단계: requirements

일반 기능 명세의 requirements 안내를 따르되, **코드가 원본**이라는 점이 다릅니다.

## 읽을 것

1. `<BASE>/../spec/stages/requirements.md` — 일반 기능 명세 requirements 안내. 아래 "다른 점" 외에는 그대로 따릅니다
2. `<BASE>/../../rules/adopt.md`의 "1단계: requirements"
3. `<BASE>/../../rules/feature/requirements-format.md`
4. `<BASE>/../../examples/order/requirements.md`

## 다른 점

1. **분기 목록부터 만듭니다.** 규칙 파일의 "분기 목록 만들기"대로, Requirement(진입점)마다 코드를 끝까지 따라가 분기 목록을 만듭니다.
   - 에러 코드 정의 파일의 코드 목록과 대조해, 이 기능에서 나올 수 있는 코드가 모두 목록에 있는지 확인합니다.
   - 기존 테스트도 읽습니다. 테스트가 검증하는 동작이 분기 목록에 없으면 분기를 놓친 것입니다.

2. **순서는 코드 순서입니다.** 일반 안내의 2번(처리 흐름의 순서 정하기)에서 순서를 새로 정하지 않습니다. 코드 실행 순서대로 쓰고, 확인 순서 표와 다른 곳을 찾아 Open Questions에 "확인 순서를 바꿀지 (기준 번호)"로 올립니다.

3. **동작을 바꾸지 않습니다.**
   - 이상해 보이는 동작, 버그로 보이는 동작도 실제 동작대로 씁니다. Open Questions에 올리고, 버그면 "bugfix 후보"라고 덧붙입니다.
   - 사용자에게 묻는 것은 비즈니스 결정이 아니라 **코드의 의도**입니다. 예: "이 분기는 일부러 이렇게 한 것인지".
   - 정책 수치(한도, 시간, 개수)는 코드와 설정에서 찾아 씁니다. 잠정값을 지어내지 않습니다.

4. **대조표를 만듭니다.** 다 쓴 뒤 분기 목록 ↔ 기준 대조표를 만들고, 빈 칸이 0개가 될 때까지 고칩니다.

5. **리뷰 단계 이름은 `adopt-requirements`**입니다. 리뷰어에게 관련 코드 경로와 에러 코드 정의 파일 경로를 꼭 넣습니다. 리뷰어가 분기 목록을 **따로 다시 만들어** 대조하게 합니다.

## 보고

일반 안내의 보고 항목에 다음을 더합니다.

- 분기 목록 ↔ 기준 대조표 (빈 칸 0개)
- 코드 순서가 확인 순서 표와 다른 곳
- bugfix 후보 (Open Questions 중 버그로 보이는 것)
