# adopt: 명세 지도

프로젝트 전체를 명세로 옮길 때 첫 단계입니다. 기능을 나누고 순서를 정해 `<specRoot>/README.md`에 씁니다. 이 단계에서는 기능 명세를 쓰지 않습니다.

## 읽을 것

1. `<BASE>/../../rules/spec-map.md` — 형식, 기능을 나누는 기준, 순서를 정하는 기준
2. `<BASE>/../../examples/README.md` — 정답 예제

## 절차

1. **진입점을 모두 찾습니다.** 설정 `techContext` 문서, 빌드 파일, 소스 트리를 보고 프로젝트의 진입점 목록을 만듭니다.
   - 외부 요청을 받는 곳 (API, 화면 처리, 메시지 수신)
   - 정해진 때 도는 일 (배치, 스케줄러)
   - 이벤트 처리 (리스너, 구독자, 웹훅)
   - 명령줄 진입점

   진입점마다 위치(파일 · 메서드)와 하는 일을 한 줄로 적습니다. 이 목록은 보고에 넣습니다.

2. **기능으로 묶습니다.** 규칙 파일의 "기능을 나누는 기준"을 따릅니다.
   - 같은 대상을 같은 규칙으로 다루는 진입점을 한 기능으로 묶습니다.
   - 기능 하나가 Requirement 10개, 기준 100개를 넘을 것 같으면 나눕니다.
   - 기술 공통 코드는 기능이 아닙니다.
   - 어느 기능에도 넣지 않은 진입점은 Out of Scope에 이유와 함께 적습니다. **목록의 모든 진입점이 어딘가에 있어야 합니다.**

3. **기능 사이 관계와 순서를 정합니다.** 한 기능의 결과로 다른 기능이 따라 바뀌는 관계를 "관련 기능"에 씁니다. 다른 기능이 참조하는 기능을 앞에 둡니다.

4. **이미 명세가 있는 기능**은 그 이름 그대로 지도에 넣습니다. adopt 대상이 아니라 일반 기능 명세입니다.

5. **작성하고 검사합니다.** `SM scaffold map`으로 골격을 만든 뒤 채우고, `SM map`의 오류를 0건으로 만듭니다.

6. **독립 리뷰를 받습니다.** `<BASE>/../../rules/workflow.md`의 "리뷰"를 따릅니다. 단계는 `adopt-map`이고, 지도 경로와 소스 루트를 넣습니다. 빠진 진입점과 잘못 묶인 기능을 찾게 합니다.

## 보고

- 찾은 진입점 수와, 기능별 진입점 목록
- 기능 목록: 순서, 이름, 예상 Requirement 수, 관련 기능
- Out of Scope와 이유
- 나누는 방식에서 판단이 필요한 곳 (두 기능 중 어디에 넣을지 애매한 진입점 등)
- 리뷰 결과 표 (지적 / 처리 / 이유)
- 승인 뒤 할 일: `/spec-mirror:adopt <첫 기능>`

지도는 단계 승인 기록을 남기지 않습니다. 사용자가 대화에서 승인하면 첫 기능으로 넘어갑니다.
