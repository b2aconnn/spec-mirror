# spec-mirror: sync

문서와 코드가 다르면 **문서가 맞다**고 봅니다. 단, 코드 쪽이 의도된 것으로 보이면 고치기 전에 사용자에게 묻습니다.

## 경로

이 스킬을 불러올 때 표시되는 **Base directory**를 `<BASE>`라고 합니다.

- 검사기: `node "<BASE>/../../scripts/spec-mirror.mjs"` (아래에서 `SM`)
- 규칙: `<BASE>/../../rules/traceability.md`

## 절차

1. **규칙을 읽습니다.** `rules/traceability.md`를 처음부터 끝까지 읽습니다.

2. **형식 검사를 합니다.** `SM check <이름>`에 오류가 있으면 먼저 보고합니다. 문서 형식이 깨진 채로 대조하지 않습니다.

3. **기계 대조를 합니다.** `SM trace <이름>`을 실행합니다.
   - 기능 명세: 기준별 테스트·코드 위치, 코드에만 있는 번호, 처리 흐름 주석 순서, 코드에서 찾지 못한 메시지
   - 버그 명세: 기대 동작별 테스트·코드 위치, 유지할 동작별 테스트. 연결된 기능 명세도 `SM trace <기능>`으로 대조합니다

4. **사람 눈으로 대조합니다.** 기계 대조가 못 잡는 것을 기준마다 확인합니다.
   - 에러 코드와 상태가 문서와 같은가 (테스트의 기대값과 코드의 실제 값 모두)
   - 상태 변화가 문서와 같은가
   - 외부 시스템 결과 갈래의 순서: 성공 → 확정 실패 → 일시 실패 → 결과 불명 → 예상하지 못한 오류
   - 주석은 없지만 코드에 있는 분기 (검증, 거절, 상태 변경, 로그). 진입점부터 따라가며 찾습니다.
   - design의 "도메인 용어 ↔ 코드" 표가 실제 코드 이름과 같은가
   - 버그 명세: 고친 동작이 기능 명세에 반영되었는가 (tasks의 "명세 반영")

5. **표로 먼저 보고합니다.** 고치기 전에 다음 표를 보여 줍니다. 불일치가 있는 행만 보여 주고, 맨 위에 전체 기준 수와 일치 수를 씁니다.

   | 기준 | 테스트 | 코드 | 불일치 내용 |
   |---|---|---|---|

   불일치마다 처리 방침을 함께 적습니다.
   - 문서에만 있음 → 테스트·코드 추가
   - 코드에만 있음 → **문서에 추가할지 코드에서 지울지 사용자에게 묻습니다**
   - 둘 다 있으나 다름 → 문서 기준으로 테스트 → 코드 순서로 고침
   - 순서 다름 → 코드 분기 순서 정리 (동작이 바뀌면 묻습니다)

6. **고칩니다.**
   - `--report-only`면 여기서 멈춥니다.
   - 사용자에게 물어야 하는 항목을 먼저 모아서 묻습니다.
   - 나머지는 테스트 → 코드 순서로 고칩니다.
   - 문서를 고쳐야 하는 결정이 나오면 `/spec-mirror:spec` 또는 `/spec-mirror:bugfix`로 문서부터 고치고 재승인을 받습니다.

7. **확인합니다.** 전체 테스트를 실행하고 `SM trace <이름>`을 다시 실행합니다. 결과를 그대로 보고합니다. 실패가 남으면 출력과 함께 보고합니다.
