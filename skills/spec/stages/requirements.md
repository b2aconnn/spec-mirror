# 기능 명세 1단계: requirements

requirements.md는 **비즈니스 규칙의 원본**입니다. 이 단계에서는 기술을 정하지 않습니다.

## 읽을 것

아래 파일을 **처음부터 끝까지** 읽습니다.

1. `<BASE>/../../rules/feature/requirements-format.md` — 형식과 문장 규칙
2. `<BASE>/../../rules/workflow.md` — 단계와 승인, 응답 뒤에 따라 일어나는 일
3. `<BASE>/../../examples/order/requirements.md` — 정답 예제. 문장 수준, 세부 항목 쓰는 법, 갈래 쓰는 법을 이 문서에 맞춥니다

## 절차

1. **기존 기능을 바꾸는 경우 코드를 먼저 읽습니다** (문장 규칙 11).
   - 진입점부터 끝까지 따라가며 기존 분기를 목록으로 만듭니다: 검증, 거절, 상태 변경, 결과별 응답, 로그.
   - 기존 에러 코드 정의에서 코드와 메시지를 그대로 가져옵니다 (문장 규칙 10).
   - 새 분기는 코드에서 들어갈 위치에 끼워 넣습니다.
   - 기존 동작이 이상해 보여도 문서에는 실제 동작대로 쓰고 Open Questions에 올립니다 (문장 규칙 13).

2. **처리 흐름의 순서부터 정합니다.** 기준을 쓰기 전에 Requirement마다 흐름의 뼈대를 먼저 만듭니다.
   - 규칙 파일의 "처리 흐름의 순서 정하기"에 있는 확인 순서 표에 이 기능의 확인과 동작을 하나씩 놓습니다. 해당 없는 단계는 건너뜁니다.
   - 같은 단계 안에서는 넓은 것 → 좁은 것, 회원이 고칠 수 있는 것 → 없는 것, 끝난 상태 → 진행 중 → 실패·취소 순서로 둡니다.
   - 표와 다르게 둬야 하는 비즈니스 이유가 있으면 그 기준에 `이유:`를 씁니다.
   - 기존 기능이면 코드 순서가 우선입니다. 코드 순서가 표와 다르면 그대로 쓰고 Open Questions에 올립니다.
   - 뼈대를 위에서 아래로 읽었을 때 메서드의 분기 순서가 그려지는지 확인합니다. 그려지지 않으면 기준을 더 나누거나 순서를 고칩니다.

3. **모르는 것을 모아서 한 번에 묻습니다.**
   - 비즈니스 결정(한도, 기한, 허용 범위, 거절 문구, 누락·중복 허용 여부)은 사용자에게 묻습니다.
   - 답이 없으면 합리적인 잠정값을 기준에 넣고 Open Questions에 "값 (기준 번호)"로 올립니다.

4. **작성합니다.**
   - 새 명세면 `SM scaffold <이름> requirements`로 골격을 만든 뒤 채웁니다. 자리표시자(`<...>`)를 모두 실제 내용으로 바꿉니다.
   - Requirement 순서: 요청을 받는 Requirement → 그 결과로 따라 바뀌는 Requirement → 배치·이벤트 → 흐름이 없는 Requirement(상태 일관성 등)
   - 처리 흐름은 2번에서 정한 순서 그대로 씁니다. 외부 시스템 결과 갈래는 성공 → 확정 실패 → 일시 실패 → 결과 불명 → 예상하지 못한 오류 순서입니다.
   - 규칙 파일의 "코드로 옮기기 좋게 쓰기"를 따릅니다: 기준 하나에 판단 하나, 확인 · 동작 · 응답을 섞지 않기, 통과한 뒤 하는 일도 기준으로.

5. **기계 검사를 통과시킵니다.**
   - 저장할 때마다 훅이 검사합니다. 알린 오류는 바로 고칩니다.
   - `SM check <이름>`의 **오류를 0건**으로 만듭니다.
   - 경고는 하나씩 보고 고칩니다. 의도한 것이면 보고 목록에 이유와 함께 넣습니다.

6. **스스로 점검합니다.** Requirement마다 규칙 파일의 "작성 후 점검" 항목을 모두 확인합니다.

7. **독립 리뷰를 받습니다.** `<BASE>/../../rules/workflow.md`의 "리뷰"를 따릅니다. 첫 리뷰는 항상 하고, 단계는 `requirements`, (기존 기능 변경이면) 관련 코드 경로도 넣습니다. 구조가 바뀐 경우에만 바뀐 Requirement를 다시 리뷰합니다.

## 보고

- Requirement 목록 (번호, 이름, 기준 수)
- Requirement마다 처리 흐름의 뼈대: 단계 순서를 한 줄로 (예: `형식 → 대상 → 권한 → 금액 → 상태 → 기한 → 변경 → PG 요청 → 결과 갈래`). 확인 순서 표와 다르게 둔 곳과 그 이유
- 잠정값과 Open Questions
- 리뷰 결과 표 (지적 / 처리 / 이유)
- 남은 경고와 이유
- design 단계에서 다룰 기술 메모 (있으면)

## 하지 않는 것

- 기술 용어(API 경로, HTTP 메서드, 클래스·테이블 이름, 트랜잭션, 메시지 큐)를 쓰지 않습니다.
- design.md나 tasks.md를 이 단계에서 만들지 않습니다.
- 코드를 고치지 않습니다.
