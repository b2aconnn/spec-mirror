# 기능 명세 2단계: design

design은 requirements의 도메인 용어와 기준을 **코드에 연결**하는 문서입니다. requirements에 없는 동작을 design에서 새로 만들지 않습니다.

## 읽을 것

1. `<BASE>/../../rules/feature/design-format.md` — 파일 구성과 섹션 규칙, 기술 정보 찾기
2. `<BASE>/../../rules/traceability.md` — 테스트 이름과 코드 주석
3. `<BASE>/../../examples/order/design.md`와 `<BASE>/../../examples/order/design/` — 형식 기준. 예제의 기술 스택은 따라 하지 않습니다

## 절차

1. **단계 잠금을 확인합니다.** `SM gate <이름> design`이 실패하면 멈추고 requirements 승인부터 안내합니다.

2. **requirements를 읽고 목록을 만듭니다.**
   - Glossary 용어 전체
   - 모든 기준 `N.M`과 각 기준의 에러 코드·메시지·로그·상태 변화
   - 외부 시스템과 정책 수치

3. **기술 맥락을 찾습니다.** 규칙 파일의 "기술 정보 찾기" 순서를 따릅니다.
   1. 설정 `techContext`의 문서
   2. 빌드 파일
   3. 같은 종류의 기존 코드
   4. 이 세션에서 쓸 수 있는 기술 전용 스킬

   정할 수 없는 기술 선택은 **추측하지 말고** 선택지와 추천을 들어 사용자에게 묻습니다. 근거로 삼은 파일은 01 Architecture 첫 문단에 남깁니다.

4. **작성합니다.**
   - `SM scaffold <이름> design`으로 목차 + 8개 파일의 골격을 만든 뒤 채웁니다.
   - 순서: 01 → 08 → 마지막에 design.md Overview
   - 02: 컴포넌트 순서는 요청이 흐르는 순서이고, 메서드 안의 확인 순서는 requirements 처리 흐름 순서와 같습니다.
   - 03: `### 도메인 용어 ↔ 코드` 표에 Glossary 용어를 **모두** 넣습니다.
   - 04: 에러 코드와 메시지를 requirements와 **글자까지 같게** 옮기고, 모든 `로그:` 항목을 로깅 표에 넣습니다.
   - 05: 테스트 묶음 표와 테스트 기준 데이터를 씁니다. 모든 경계값에 그 값을 만드는 데이터가 있어야 합니다.
   - 07: Prework 제목은 기준 문장 그대로입니다. PROPERTY로 분류한 기준은 모두 어떤 Property의 Validates에 넣습니다.
   - 해당 없는 섹션은 제목을 남기고 "해당 없음 — <이유>"라고 씁니다.

5. **기계 검사를 통과시킵니다.** `SM check <이름>`의 **오류를 0건**으로 만듭니다 (REQ·DES 규칙 모두).

6. **requirements와 대조합니다.** 아래 표를 만들어 빈 칸이 없는지 확인합니다.

   | 기준 | 구현 위치(컴포넌트·메서드) | 테스트 묶음 | Property |
   |---|---|---|---|

   - 칸이 비면 design을 보완합니다.
   - requirements에 없는 분기가 필요해 보이면 design에 넣지 말고 "requirements 보완 필요"로 보고합니다.

7. **독립 리뷰를 받습니다.** `<BASE>/../../rules/workflow.md`의 "리뷰"를 따릅니다. 단계는 `design`, requirements·design 경로를 넣습니다.

## 보고

- 핵심 설계 결정: 기술 선택과 근거, 트랜잭션·외부 호출 경계, 동시성 처리
- requirements 보완이 필요한 항목
- 리뷰 결과 표 (지적 / 처리 / 이유)
- 남은 경고

## 하지 않는 것

- requirements를 몰래 고치지 않습니다. 고쳐야 하면 멈추고 묻습니다. 고친 뒤에는 requirements 재승인이 필요합니다.
- 정해진 8개 파일 외의 design 파일을 만들거나 섹션 순서를 바꾸지 않습니다.
- 코드를 고치지 않습니다.
