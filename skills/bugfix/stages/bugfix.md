# 버그 명세 1단계: bugfix

bugfix.md는 버그를 **현재 동작 · 기대 동작 · 유지할 동작**으로 나눠 도메인 언어로 씁니다. 원인과 코드는 design에서 다룹니다.

## 읽을 것

1. `<BASE>/../../rules/bugfix/bugfix-format.md` — 형식, 항목 규칙, 명세 연결
2. `<BASE>/../../rules/feature/requirements-format.md`의 "문장 규칙" — 문장은 requirements와 같은 규칙입니다
3. `<BASE>/../../examples/confirm-recheck-mismatch/bugfix.md` — 정답 예제

## 절차

1. **버그 설명에서 네 가지를 모읍니다.**
   - 재현 방법 (어떤 요청·상태·데이터에서)
   - 지금 결과 (응답, 상태, 로그)
   - 기대 결과
   - 바뀌면 안 되는 것 (사용자가 말한 제약, 건드리면 안 되는 코드)

   빠진 것이 있으면 코드와 명세로 먼저 찾아보고, 그래도 모르는 것만 **한 번에 모아서** 묻습니다.

2. **관련 기능 명세를 찾습니다.**
   - `SM list`로 기능 명세 목록을 보고, 이 동작을 정하는 requirements 기준을 찾습니다.
   - 기능 명세와 지금 코드가 다르면 "명세대로 고친다"가 기대 동작입니다.
   - 기능 명세에 없는 경우면 기대 동작을 사용자와 정하고 `명세: 새 기준 (<기능>)`으로 씁니다.
   - 기능 명세가 없으면 `명세: 없음`입니다.

3. **코드에서 재현 경로를 따라갑니다.** 원인을 확정하려는 것이 아니라 **유지할 동작**을 찾으려는 것입니다.
   - 같은 분기의 다른 갈래 (예: 성공, 다른 실패 사유)
   - 같은 결과를 내는 다른 경로 (예: 승인 응답 경로와 즉시 조회 경로)
   - 같은 코드를 함께 쓰는 다른 호출자 (예: 배치, 다른 API)

   이 경우들이 3.M이 됩니다. 기존 테스트가 있으면 이름을 적어 둡니다 (design에서 씁니다).

4. **작성합니다.**
   - `SM scaffold <이름> bugfix`로 골격을 만든 뒤 채웁니다. 자리표시자(`<...>`)를 모두 바꿉니다.
   - 현재 동작마다 `재현:`을 씁니다. 기대 동작은 현재 동작과 같은 수이고, `2.N`이 `1.N`을 고친 모습입니다.
   - 유지할 동작은 "**… 지금처럼 …**"으로 씁니다.
   - 기대 동작·유지할 동작에는 `명세:`를 씁니다. 기능 기준은 항상 `order 6.21`처럼 기능 이름을 붙입니다.

5. **기계 검사를 통과시킵니다.** `SM check <이름>`의 **오류를 0건**으로 만들고, 경고는 고치거나 이유를 보고합니다.

6. **스스로 점검합니다.** 규칙 파일의 "작성 후 점검" 다섯 항목을 확인합니다.

7. **독립 리뷰를 받습니다.** `<BASE>/../../rules/workflow.md`의 "리뷰"를 따릅니다. 단계는 `bugfix`, 관련 기능 명세 경로와 관련 코드 경로도 넣고, 특히 "빠진 유지할 동작"을 찾게 합니다.

## 보고

- 현재 동작 → 기대 동작 짝 (번호와 한 줄 요약)
- 유지할 동작 목록과, 각각을 정한 기능 명세 기준
- 고치면서 바뀔 기능 명세 기준 (명세 반영 대상)
- 남은 경고와 Open Questions
- 리뷰 결과 표 (지적 / 처리 / 이유)

## 하지 않는 것

- 원인, 코드 위치, 고치는 방법을 bugfix.md에 쓰지 않습니다. design에서 씁니다.
- 코드를 고치지 않습니다. 재현을 위해 테스트를 실행해 보는 것은 괜찮습니다.
