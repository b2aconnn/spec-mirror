# 버그 명세 2단계: design

버그 design은 **코드를 읽어 원인을 찾고, 고치는 범위를 최소로 정하고, 무엇으로 확인할지** 정합니다. design.md 한 파일입니다.

## 읽을 것

1. `<BASE>/../../rules/bugfix/design-format.md` — 섹션과 규칙
2. `<BASE>/../../rules/traceability.md`의 "버그 명세" — 테스트 이름
3. `<BASE>/../../examples/confirm-recheck-mismatch/design.md` — 정답 예제

## 절차

1. **단계 잠금을 확인합니다.** `SM gate <이름> design`이 실패하면 멈추고 bugfix 승인부터 안내합니다.

2. **원인을 찾습니다. 반드시 코드를 읽습니다.**
   - 재현 경로를 진입점부터 따라가며 1.M의 결과가 어디서 만들어지는지 찾습니다.
   - 읽어서 확인한 것은 "확인됨", 확인하지 못한 것은 "가설"로 적습니다.
   - 직접 원인과 원인이 드러나는 경로가 다르면 둘 다 적고, 어느 쪽을 고칠지 정합니다.
   - 원인이 여러 곳이거나 확신이 없으면, 재현 테스트를 잠시 실행해 확인해도 됩니다. 이 단계에서 코드를 고치지는 않습니다.

3. **버그 조건을 정합니다.** `isBugCondition(input)`을 관찰 가능한 값으로 씁니다. 참이면 1.M, 거짓이면 3.M의 범위입니다.

4. **고치는 범위를 정합니다.**
   - 유지할 동작(3.M)을 하나씩 보며, 고칠 곳이 그 동작을 바꾸지 않는지 확인합니다.
   - 같은 코드를 쓰는 다른 호출자가 있으면, 그 호출자의 동작이 바뀌지 않는 위치를 고릅니다.
   - "바꾸지 않는 것"과 그 이유를 씁니다.

5. **Property를 씁니다.**
   - Bug Condition Property는 모든 2.M을, Preservation Property는 모든 3.M을 검증합니다.
   - 이름은 `Bug Condition - <이름>` / `Preservation - <이름>`입니다.

6. **Testing Strategy를 씁니다.**
   - 탐색 테스트의 Test Cases와 **Expected Counterexamples**(고치기 전에 나올 잘못된 결과)
   - Fix Checking, Preservation Checking 의사 코드
   - 테스트 이름: 기능 명세와 연결된 동작은 그 기준의 `R{N}-{M}`(새 테스트는 접미사), 기존 테스트가 있는 유지할 동작은 그 테스트 이름

7. **작성하고 검사합니다.** `SM scaffold <이름> design`으로 골격을 만든 뒤 채우고, `SM check <이름>`의 **오류를 0건**으로 만듭니다.

8. **독립 리뷰를 받습니다.** `<BASE>/../../rules/workflow.md`의 "리뷰"를 따릅니다. 단계는 `bugfix-design`, 관련 코드 경로도 넣고, 원인 분석이 코드와 맞는지와 고치는 위치가 유지할 동작을 깨지 않는지 확인하게 합니다.

## 보고

- 원인 (확인됨 / 가설)과 근거 코드 위치
- 고치는 곳과 바꾸지 않는 곳, 그 이유
- 탐색 테스트가 고치기 전에 보일 것으로 예상하는 반례
- 고친 뒤 바뀌어야 할 기능 명세 기준
- 리뷰 결과 표 (지적 / 처리 / 이유)

## 하지 않는 것

- bugfix.md에 없는 동작을 고치지 않습니다. 고칠 것이 더 보이면 bugfix.md 보완으로 보고합니다.
- 코드를 고치지 않습니다.
