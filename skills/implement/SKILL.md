# spec-mirror: implement

## 경로

이 스킬을 불러올 때 표시되는 **Base directory**를 `<BASE>`라고 합니다.

- 검사기: `node "<BASE>/../../scripts/spec-mirror.mjs"` (아래에서 `SM`)
- 규칙: `<BASE>/../../rules/traceability.md`, 버그 명세면 `<BASE>/../../rules/bugfix/tasks-format.md`도 읽습니다

## 절차

1. **단계 잠금을 확인합니다.** `SM gate <이름> implement`가 실패하면 멈추고 어느 단계 승인이 필요한지 알립니다.

2. **규칙을 읽습니다.** `rules/traceability.md`를 처음부터 끝까지 읽습니다. `SM next <이름> --json`의 `type`이 `bugfix`면 `rules/bugfix/tasks-format.md`도 읽습니다.

3. **할 태스크를 고릅니다.**
   - 인자가 번호면 그 태스크를 합니다.
   - `next`이거나 인자가 없으면 `SM next <이름> --json`의 `task`를 합니다.
   - `all`이면 차례로 진행하되 **Checkpoint마다 멈추고** 보고합니다.
   - 선택(`*`) 태스크는 사용자가 요청할 때만 합니다.
   - Dependency Graph에서 앞 wave가 끝나지 않은 태스크는 하지 않습니다.
   - 시작하는 태스크는 `[-]`(진행 중)로 표시합니다.

4. **프로젝트 관례를 확인합니다.**
   - 언어, 테스트 도구, 테스트 실행 명령, 주석 문법, 가짜 구현(fake)·고정 시계 위치
   - 찾는 곳: design(기능은 05·08, 버그는 Testing Strategy), 설정 `techContext` 문서, 기존 테스트
   - 테스트 실행 명령을 찾을 수 없으면 사용자에게 묻습니다.

5. **태스크 종류별로 진행합니다.**

   **기능 명세**
   - **인수 테스트 작성**
     - 기준마다 `R{N}-{M} <기준 요약>` 이름으로 테스트를 씁니다.
     - 상태, 에러 코드, 메시지, 상태 변화, 외부 호출 횟수, 로그를 검증합니다. 데이터는 design 05의 테스트 기준 데이터를 씁니다.
     - 실행해서 **실패를 확인합니다 (Red).** 이미 통과하면 이유를 확인해 보고합니다.
   - **구현**
     - design 02의 인터페이스대로 구현합니다.
     - 처리 흐름 기준은 분기 바로 위에 `R{N}-{M}` 주석을 **번호 순서대로** 답니다. 항상 지켜야 할 규칙은 보장 위치에 답니다.
     - 에러 메시지는 requirements와 글자까지 같게 씁니다.
     - 관련 테스트를 실행해 **통과를 확인합니다 (Green).**

   **버그 명세**
   - **1. 버그 조건 탐색 테스트**
     - 테스트는 **기대 동작**을 검증합니다. 이름은 [추적 규칙](../../rules/traceability.md#버그-명세)을 따릅니다.
     - 고치기 전 코드에서 실행해 **실패해야 합니다.** 실패 내용·반례를 태스크 아래에 `  - 결과: <실패 내용>`으로 남깁니다.
     - **통과하면 멈춥니다.** 원인 분석이 틀렸거나 테스트가 버그 조건을 만들지 못한 것입니다. 사용자에게 보고하고 design을 다시 봅니다.
     - 테스트를 기대 동작과 다르게 고쳐서 실패시키거나 통과시키지 않습니다.
   - **2. 보존 테스트**
     - 고치기 전 코드에서 **통과해야 합니다.** 실패하면 보존 테스트가 지금 동작을 잘못 적은 것입니다. 테스트를 지금 동작에 맞추고, 그 동작이 bugfix.md 3.M과 다르면 사용자에게 보고합니다.
   - **3. 버그 수정**
     - **1번이 실패로, 2번이 통과로 확인된 뒤에만** 고칩니다.
     - design "Fix Implementation"의 범위만 고칩니다. "바꾸지 않는 것"은 건드리지 않습니다.
     - 확인 태스크에서는 1·2번 테스트를 **고치지 않고** 다시 실행합니다. 탐색 테스트는 통과, 보존 테스트는 계속 통과해야 합니다.
   - **4. 명세 반영**
     - 기능 명세 requirements(필요하면 design)를 고친 동작에 맞춥니다. 기능 명세의 형식 규칙을 따릅니다.
     - 고친 기능 명세는 재승인이 필요합니다. 사용자에게 승인을 요청하고, 승인하면 `SM approve <기능> requirements`를 실행합니다.

   **adopt 명세** (`SM next <이름> --json`의 `mode`가 `adopt`)
   - **코드 동작을 바꾸지 않습니다.** 할 일은 테스트 이름 정리, 빠진 인수 테스트 추가, 분기 주석뿐입니다.
   - **기존 테스트 정리**: 이름을 `R{N}-{M} <요약>`으로 바꾸고, 검증 내용이 기준과 같은지 확인합니다. 이름만 바꾸고 검증 내용은 바꾸지 않습니다. 기준과 다르면 멈추고 보고합니다.
   - **빠진 인수 테스트 추가**: 새 테스트는 **지금 코드에서 바로 통과해야 합니다.** 실패하면 코드를 고치지 않고 멈춥니다. 원인이 명세면 requirements를 고치고, 코드면 Open Questions(bugfix 후보)로 보고합니다(`rules/adopt.md`의 "새 인수 테스트가 실패하면").
   - **코드 주석**: design 02의 `기준 ↔ 코드 분기` 표에 따라 분기 바로 위에 `R{N}-{M}`을 답니다. 주석 말고는 코드를 바꾸지 않습니다.
   - 태스크마다 전체 테스트가 그대로 통과하는지 확인합니다.

   **Checkpoint**
   - 전체 테스트를 실행합니다.
   - `SM trace <이름>`으로 지금까지 구현한 범위의 불일치를 확인합니다. 버그 명세면 관련 기능 명세도 `SM trace <기능>`으로 확인합니다.
   - 결과를 보고하고 멈춥니다.

6. **태스크를 체크합니다.** 끝난 태스크를 `[x]`로 바꿉니다. 모든 필수 하위 태스크가 끝나면 상위 태스크도 체크합니다. 체크 표시와 `결과:` 줄은 tasks 승인에 영향을 주지 않습니다.

7. **보고합니다.** 한 일, 테스트 결과(실패가 있으면 출력 그대로), 다음 태스크를 보고합니다.

## 명세와 다를 때

- 구현 중에 명세에 없는 분기가 필요하거나 명세가 틀려 보이면 **멈추고** 보고합니다. 코드에만 있는 분기를 만들지 않습니다.
- 사용자가 명세 변경에 동의하면 `/spec-mirror:spec`(기능) 또는 `/spec-mirror:bugfix`(버그)로 문서부터 고치고, 재승인 뒤 이어서 진행합니다.
