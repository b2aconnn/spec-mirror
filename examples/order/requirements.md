# Requirements Document

## Introduction

회원이 상품과 수량을 골라 **주문**하고, 시스템이 계산한 주문 금액으로 **결제**하는 기능입니다.
결제 결과(승인 완료·결제 실패)는 주문 상태에 함께 반영되며, 결제 전 주문은 회원이 취소하거나 결제 기한이 지나면 자동으로 만료됩니다.

- 결제는 주문이 접수될 때 함께 준비됩니다. 회원이 금액을 정해 결제를 준비하던 기존 방식은 없앱니다.
- 범위 밖: 결제 완료 주문의 취소·환불, 부분 취소, 재고 차감, 쿠폰·포인트, 결제 실패 주문의 재결제(새 주문으로 대체)
- API 경로, 클래스, 테이블 등 구현 정보는 [design.md](design.md)에 있습니다.

## Glossary

- **회원 (Member)**: 주문하고 결제하는 사용자. 자신의 주문만 보고 다룰 수 있다
- **상품 (Product)**: 판매 대상. 상품명, 판매가, 판매 여부를 가진다
- **상품 카탈로그 (Product Catalog)**: 상품 정보를 제공하는 외부 시스템. 주문 시스템은 조회만 한다
- **주문 (Order)**: 회원이 구매하려는 주문 항목 목록과 시스템이 확정한 주문 금액. 주문 하나에 결제 하나가 대응한다
- **주문 접수**: 주문 요청이 모든 규칙을 통과해 주문이 만들어지는 것. 규칙을 하나라도 어기면 "주문을 받지 않는다"
- **주문번호 (Order ID)**: 주문을 식별하는 번호. `ORD_` + 26자. PG에 보내는 주문번호와 같은 값이다
- **주문 항목 (Order Item)**: 주문 안의 상품 한 종류와 수량. 주문 시점의 상품명과 판매가를 그대로 보관한다 (가격 스냅샷)
- **항목 금액 / 주문 금액**: 항목 금액 = 판매가 × 수량, 주문 금액 = 모든 항목 금액의 합. 항상 시스템이 계산한다
- **주문명 (Order Name)**: PG 결제창에 보여줄 주문 이름. 예: `아메리카노 외 1건`
- **주문 상태 (Order Status)**
  - 결제 대기 (`PENDING_PAYMENT`): 주문이 접수됐고 결제가 끝나지 않음
  - 결제 완료 (`PAID`): 결제가 승인됨
  - 결제 실패 (`PAYMENT_FAILED`): 결제가 실패로 확정됨
  - 주문 취소 (`CANCELED`): 결제 전에 회원이 취소함
  - 기한 만료 (`EXPIRED`): 결제 기한까지 결제가 시작되지 않음
  - 결제 대기 외에는 모두 **종결 상태**이며, 종결된 주문의 상태는 다시 바뀌지 않는다
- **결제 (Payment)**: 주문 금액을 PG로 결제하는 건. 결제 금액은 항상 주문 금액과 같다
- **결제 상태 (Payment Status)**
  - 승인 대기 (`READY`): 결제창에서 회원 인증을 기다리는 중. 아직 PG에 승인 요청 전
  - 승인 진행 중 (`IN_PROGRESS`): PG에 승인을 요청하고 응답을 기다리는 중
  - 결과 확인 중 (`UNKNOWN`): 승인 요청 결과를 알 수 없음 (타임아웃 등). 돈이 나갔을 수도 있다
  - 승인 완료 (`DONE`): PG가 승인함
  - 결제 실패 (`FAILED`): 승인되지 않음이 확정됨
- **결제 실패 사유 (Fail Code)**: 결제가 실패한 이유. PG 거절 코드, `PG_RESPONSE_MISMATCH`, 그리고 주문 쪽 사유인 `ORDER_CANCELED`(주문 취소), `ORDER_EXPIRED`(기한 만료)
- **결제 기한 (Expires At)**: 주문 접수 시각 + 30분. 이 시각까지 결제 승인이 시작되지 않으면 주문은 만료된다
- **결제 승인 (Confirm)**: 회원이 결제창 인증을 마친 뒤 시스템이 PG에 최종 승인을 요청하는 것
- **대사 (Reconciliation)**: 결과 확인 중인 결제를 PG 조회로 승인 완료 또는 결제 실패로 확정하는 것
- **중복 주문 방지 키 (Idempotency Key)**: 같은 주문 요청이 여러 번 와도 주문이 한 번만 접수되도록 클라이언트가 요청마다 붙이는 키
- **정합성 경보**: 주문·결제 상태가 PG와 맞지 않아 운영자가 직접 확인해야 하는 상황. ERROR 로그로 남긴다

## Requirements

### Requirement 1: 주문 접수

**User Story:** As a 회원, I want to 상품과 수량을 골라 주문할 수 있어야, so that 시스템이 확정한 금액으로 결제를 진행할 수 있다

#### Acceptance Criteria

##### 처리 흐름

1. **회원은 상품과 수량을 골라 주문할 수 있다.**
   - 요청 정보: 주문 항목 목록(상품, 수량), 중복 주문 방지 키

2. **주문 상품은 1개 이상 20개 이하로 담을 수 있다.** 비어 있거나 20개를 넘으면 주문을 받지 않는다.
   - 경계: 20개 가능, 21개 불가
   - 에러: `400` `INVALID_ORDER_ITEM_COUNT`
   - 메시지: "주문 상품은 1개 이상 20개 이하로 담아주세요."

3. **상품별 수량은 1개 이상 99개 이하로 담을 수 있다.** 범위를 벗어나면 주문을 받지 않는다.
   - 경계: 1개·99개 가능, 0개·100개 불가
   - 에러: `400` `INVALID_ORDER_QUANTITY`
   - 메시지: "상품별 수량은 1개 이상 99개 이하로 선택해주세요."

4. **같은 상품은 한 번만 담을 수 있다.** 같은 상품이 여러 항목에 있으면 합치지 않고 주문을 받지 않는다.
   - 에러: `400` `DUPLICATED_ORDER_ITEM`
   - 메시지: "같은 상품이 중복으로 담겨 있습니다."

5. **주문 상품의 상품명, 판매가, 판매 여부는 상품 카탈로그에서 확인한다.**
   - 시점: 위 항목 검증과 중복 주문 확인(Requirement 2)을 통과한 뒤

6. **상품 정보를 확인할 수 없으면 주문을 받지 않는다.** (상품 카탈로그 장애)
   - 에러: `503` `PRODUCT_CATALOG_UNAVAILABLE`
   - 메시지: "상품 정보를 확인할 수 없습니다. 잠시 후 다시 시도해주세요."

7. **존재하지 않는 상품은 주문할 수 없다.**
   - 에러: `400` `PRODUCT_NOT_FOUND`
   - 메시지: "존재하지 않는 상품이 포함되어 있습니다. ({상품 ID})"

8. **판매 중이 아닌 상품은 주문할 수 없다.**
   - 에러: `409` `PRODUCT_NOT_ON_SALE`
   - 메시지: "판매 중이 아닌 상품이 포함되어 있습니다. ({상품명})"

9. **주문 금액은 상품 카탈로그의 판매가로 계산한다.**
   - 항목 금액 = 판매가 × 수량
   - 주문 금액 = 모든 항목 금액의 합

10. **1회 주문 금액은 10,000,000원을 넘을 수 없다.**
    - 경계: 10,000,000원 가능, 10,000,001원 불가
    - 에러: `400` `ORDER_AMOUNT_LIMIT_EXCEEDED`
    - 메시지: "1회 주문 금액은 10,000,000원을 넘을 수 없습니다."

11. **주문번호는 시스템이 발급한다.**
    - 형식: `ORD_` + ULID 26자
    - 이유: 추측할 수 없어야 하고, PG 주문번호 규칙을 만족해야 한다

12. **주문명은 첫 상품명으로 정한다.** 상품이 2개 이상이면 `{첫 상품명} 외 {나머지 개수}건`으로 정한다.
    - 예: 아메리카노 2 + 카페라떼 1 → `아메리카노 외 1건`

13. **주문이 접수되면 주문, 주문 항목, 결제가 함께 만들어진다.** 하나라도 실패하면 아무것도 만들어지지 않는다.
    - 주문: 결제 대기
    - 주문 항목: 주문 시점의 상품명·판매가 (가격 스냅샷)
    - 결제: 승인 대기, 결제 금액 = 주문 금액
    - 결제 기한: 접수 시각 + 30분 (주문과 결제가 같은 값)

14. **주문이 접수되면 접수된 주문 정보를 응답한다.**
    - 응답: `201` — 주문번호, 주문 상태(결제 대기), 주문 금액, 주문명, 주문 항목, 결제 기한, 결제 상태(승인 대기)

##### 항상 지켜야 할 규칙

15. **주문 금액은 언제나 시스템이 계산한다.** 요청에 금액이 들어 있어도 쓰지 않는다.

16. **주문을 접수하는 동안 PG에는 어떤 요청도 보내지 않는다.**

17. **접수된 주문의 금액은 바뀌지 않는다.** 이후 상품 판매가가 바뀌어도 주문 금액과 주문 항목 단가는 그대로다.

### Requirement 2: 중복 주문 방지

**User Story:** As a 회원, I want to 주문 버튼을 여러 번 누르거나 네트워크가 재시도되어도 주문이 한 번만 접수되어야, so that 같은 주문이 중복으로 생기지 않는다

#### Acceptance Criteria

##### 처리 흐름

1. **중복 주문 방지 키는 반드시 있어야 한다.** 없거나 형식이 틀리면 주문을 받지 않는다.
   - 형식: 1~64자의 영문·숫자·`-`·`_`
   - 에러: `400` `INVALID_IDEMPOTENCY_KEY`
   - 메시지: "중복 주문 방지 키가 올바르지 않습니다."

2. **같은 회원이 같은 키로 접수한 주문이 있는지 먼저 확인한다.**
   - 시점: 상품 정보를 확인하기 전

3. **그 주문이 접수된 지 24시간이 지났으면 키를 다시 쓸 수 있다.** 기존 주문에서 키를 떼어 내고 새 주문 접수를 계속한다.

4. **24시간 안에 같은 주문 내용으로 다시 요청하면, 새로 접수하지 않고 기존 주문을 돌려준다.**
   - 응답: `200` — 기존 주문 정보
   - 상품 카탈로그를 조회하지 않는다

5. **24시간 안에 같은 키로 다른 주문 내용을 요청하면 주문을 받지 않는다.**
   - 에러: `422` `IDEMPOTENCY_KEY_REUSED`
   - 메시지: "이미 다른 주문에 사용된 중복 주문 방지 키입니다."

##### 항상 지켜야 할 규칙

6. **주문 내용이 같은지는 상품과 수량 구성으로만 판단한다.** 항목 순서는 따지지 않는다.
   - 예: `아메리카노 2, 카페라떼 1`과 `카페라떼 1, 아메리카노 2`는 같은 주문 내용

7. **키는 회원별로 구분한다.** 다른 회원이 같은 키를 보내면 별개의 주문으로 접수한다.

8. **같은 키로 동시에 여러 번 요청해도 주문은 하나만 접수된다.**
   - 응답: 한 요청만 `201`, 나머지는 같은 주문번호로 `200`

### Requirement 3: 주문 조회

**User Story:** As a 회원, I want to 내 주문의 상태와 결제 결과를 확인할 수 있어야, so that 결제가 끝났는지 알 수 있다

#### Acceptance Criteria

##### 처리 흐름

1. **회원은 주문번호로 자신의 주문을 조회할 수 있다.**

2. **다른 회원의 주문은 볼 수 없다.** 주문이 없을 때와 똑같이 응답한다.
   - 에러: `404` `ORDER_NOT_FOUND`
   - 메시지: "주문을 찾을 수 없습니다."
   - 이유: 다른 회원의 주문이 존재하는지조차 알려주지 않는다 (403 대신 404)

3. **주문 정보와 결제 정보를 함께 보여준다.**
   - 응답: `200`
   - 주문: 주문번호, 주문 상태, 주문 금액, 주문명, 주문 항목, 주문 일시, 결제 기한
   - 결제: 결제 상태, 결제 수단, 승인 일시, 결제 실패 사유

4. **결제를 확인 중인 주문은 결제 대기로 보여준다.** 결제 상태는 실제 상태(승인 진행 중, 결과 확인 중) 그대로 보여준다.
   - 이유: 회원이 "결제 확인 중"임을 알 수 있도록

##### 항상 지켜야 할 규칙

5. **주문 항목은 주문 시점의 상품명과 단가로 보여준다.** 조회할 때 상품 카탈로그를 조회하지 않는다.

### Requirement 4: 주문 내역 조회

**User Story:** As a 회원, I want to 내가 접수한 주문 내역을 볼 수 있어야, so that 지난 주문을 찾아볼 수 있다

#### Acceptance Criteria

##### 처리 흐름

1. **회원은 자신의 주문 내역을 페이지 단위로 볼 수 있다.**
   - 요청 정보: 페이지 번호, 페이지 크기

2. **페이지 번호는 0 이상, 페이지 크기는 1 이상이어야 한다.** 아니면 조회하지 않는다.
   - 에러: `400` `INVALID_PAGE_REQUEST`
   - 메시지: "페이지 요청이 올바르지 않습니다."

3. **한 페이지는 기본 20건, 최대 50건이다.**
   - 50건보다 많이 요청하면 50건만 보여준다

4. **최근 주문부터 주문별 요약과 다음 페이지가 있는지를 보여준다.**
   - 요약: 주문번호, 주문 상태, 주문 금액, 주문명, 주문 일시

##### 항상 지켜야 할 규칙

5. **주문 내역에는 본인의 주문만 나온다.** 다른 회원의 주문은 포함하지 않는다.

### Requirement 5: 결제 전 주문 취소

**User Story:** As a 회원, I want to 결제하기 전에 주문을 취소할 수 있어야, so that 원하지 않는 주문이 결제되지 않는다

#### Acceptance Criteria

##### 처리 흐름

1. **회원은 결제하기 전의 주문을 취소할 수 있다.**
   - 요청 정보: 주문번호

2. **다른 회원의 주문은 취소할 수 없다.** 주문이 없을 때와 똑같이 응답한다.
   - 에러: `404` `ORDER_NOT_FOUND`
   - 메시지: "주문을 찾을 수 없습니다."

3. **이미 취소된 주문을 다시 취소해도 성공으로 본다.** 아무것도 바꾸지 않는다.
   - 응답: `200` — 현재 주문 정보

4. **결제 완료, 결제 실패, 기한 만료된 주문은 취소할 수 없다.**
   - 에러: `409` `ORDER_NOT_CANCELABLE`
   - 메시지: "취소할 수 없는 주문입니다. (현재 상태: {주문 상태})"

5. **결제가 진행 중인 주문은 취소할 수 없다.** 주문은 결제 대기지만 결제가 승인 진행 중이거나 결과 확인 중인 경우다.
   - 에러: `409` `PAYMENT_IN_PROGRESS`
   - 메시지: "이미 처리 중인 결제입니다. 잠시 후 결과를 확인해주세요."
   - 이유: 돈이 나갔을 수 있으므로 결제 결과를 기다린다

6. **결제 승인 전에 주문을 취소하면 결제도 함께 실패 처리한다.**
   - 결제: 승인 대기 → 결제 실패 (실패 사유 `ORDER_CANCELED`)
   - 주문: 결제 대기 → 주문 취소

7. **취소와 결제 승인이 겹치면 먼저 확정된 쪽만 반영한다.** 취소를 확정하는 순간 결제가 이미 승인 대기가 아니면(그 사이 승인이 시작됨) 아무것도 바꾸지 않는다.
   - 에러: `409` `PAYMENT_IN_PROGRESS`
   - 메시지: "이미 처리 중인 결제입니다. 잠시 후 결과를 확인해주세요."

8. **취소가 끝나면 취소된 주문 정보를 응답한다.**
   - 응답: `200` — 주문 상태(주문 취소), 결제 상태(결제 실패), 결제 실패 사유(`ORDER_CANCELED`)

##### 항상 지켜야 할 규칙

9. **주문을 취소하는 동안 PG에는 어떤 요청도 보내지 않는다.**
   - 이유: 승인 전이므로 환불할 금액이 없다

### Requirement 6: 주문 결제 승인

**User Story:** As a 회원, I want to 결제창 인증을 마친 주문을 최종 결제할 수 있어야, so that 주문 금액이 정확히 한 번만 결제되고 결과를 바로 알 수 있다

#### Acceptance Criteria

##### 처리 흐름

1. **회원은 결제창 인증을 마친 주문의 결제 승인을 요청할 수 있다.**
   - 요청 정보: 주문번호, 결제 키, 결제 금액
   - 주문이 접수될 때 함께 만들어진 결제로 승인한다

2. **요청 내용을 확인할 수 없으면 승인하지 않는다.**
   - 조건: 회원 정보가 없음, 주문번호가 6~64자의 영문·숫자·`-`·`_`가 아님, 결제 키가 비었거나 200자를 넘음, 결제 금액이 0 이하
   - 에러: `400` `INVALID_REQUEST`
   - 메시지: "잘못된 요청입니다."
   - 예: 항목 오류면 어떤 항목인지 괄호로 덧붙는다 → "잘못된 요청입니다. (amount: 0보다 커야 합니다)"

3. **결제 정보가 없으면 승인할 수 없다.**
   - 에러: `404` `PAYMENT_NOT_FOUND`
   - 메시지: "결제 정보를 찾을 수 없습니다."

4. **다른 회원의 결제는 승인할 수 없다.**
   - 에러: `403` `FORBIDDEN_PAYMENT`
   - 메시지: "본인의 결제가 아닙니다."

5. **결제 금액은 주문 금액과 같아야 한다.** 다르면 PG에 승인을 요청하지 않고 아무것도 바꾸지 않는다.
   - 에러: `400` `AMOUNT_MISMATCH`
   - 메시지: "결제 금액이 주문 금액과 일치하지 않습니다."
   - 이유: PG 승인 뒤에 알게 되면 취소 비용이 들고 회원도 불편하다

6. **이미 승인된 결제를 같은 결제 키로 다시 요청하면, PG에 다시 요청하지 않고 기존 결과를 돌려준다.**
   - 응답: `200` — 기존 결제 결과 (17과 같은 내용)
   - 이유: 새로고침이나 네트워크 재시도로 같은 요청이 다시 와도 두 번 결제되지 않도록

7. **이미 승인된 주문은 다른 결제 키로 승인할 수 없다.**
   - 에러: `409` `PAYMENT_KEY_MISMATCH`
   - 메시지: "이미 다른 결제 건으로 승인된 주문입니다."

8. **결제가 진행 중이면 승인할 수 없다.** 결제가 승인 진행 중이거나 결과 확인 중인 경우다.
   - 에러: `409` `PAYMENT_IN_PROGRESS`
   - 메시지: "이미 처리 중인 결제입니다. 잠시 후 결과를 확인해주세요."

9. **취소되었거나 기한이 만료된 주문은 결제할 수 없다.**
   - 판단: 결제 실패 사유가 `ORDER_CANCELED` 또는 `ORDER_EXPIRED`
   - 에러: `409` `ORDER_NOT_PAYABLE`
   - 메시지: "취소되었거나 결제 기한이 지난 주문입니다. 새로 주문해주세요."

10. **이미 결제에 실패한 주문은 다시 결제할 수 없다.** (9 이외의 실패 사유)
    - 에러: `409` `ALREADY_FAILED`
    - 메시지: "이미 실패 처리된 결제입니다. 새로 결제를 시도해주세요."

11. **결제 기한이 지난 주문은 결제할 수 없다.** 아직 기한 만료 처리 전이어도 마찬가지다. 주문 상태는 바꾸지 않는다.
    - 경계: 결제 기한 정각부터 불가
    - 에러: `400` `PAYMENT_EXPIRED`
    - 메시지: "결제 가능 시간이 만료되었습니다."
    - 이유: 기한 만료 처리는 Requirement 8이 맡는다

12. **확인을 모두 통과하면 결제를 승인 진행 중으로 바꾸고 결제 키를 기록한다.**
    - 결제: 승인 대기 → 승인 진행 중

13. **승인 진행 중으로 바꾸는 순간 결제가 이미 승인 대기가 아니면 승인하지 않는다.** 동시에 온 다른 승인 요청, 주문 취소, 기한 만료가 먼저 확정된 경우다. PG에 승인을 요청하지 않는다.
    - 에러: `409` `PAYMENT_IN_PROGRESS`
    - 메시지: "이미 처리 중인 결제입니다. 잠시 후 결과를 확인해주세요."

14. **결제 키가 이미 다른 주문에 쓰였으면 승인하지 않는다.** 아무것도 바꾸지 않는다.
    - 에러: `409` `DUPLICATED_PAYMENT_KEY`
    - 메시지: "이미 다른 주문에 사용된 결제 키입니다."

15. **PG에 승인을 요청한다.** 결과는 승인 / 거절 / 미도달 / 결과 불명 중 하나로 나뉜다 (16~23).

16. **PG가 승인하면 승인 내용을 주문과 대조한다.**
    - 조건: PG의 주문번호·결제 금액·결제 키가 주문과 같고, PG 상태가 승인 완료여야 한다
    - 이유: PG 응답도 그대로 믿지 않는다

17. **대조 결과가 맞으면 결제를 승인 완료로 바꾸고 결과를 응답한다.**
    - 결제: 승인 진행 중 → 승인 완료 (결제 수단, 승인 일시 기록)
    - 주문: 7.1에 따라 결제 완료
    - 응답: `200` — 주문번호, 결제 키, 결제 상태(승인 완료), 결제 금액, 결제 수단, 승인 일시

18. **대조 결과가 다르면 PG 승인을 취소하고 결제 실패로 처리한다.**
    - PG: 승인 취소 요청 (사유 "주문 정보 불일치로 인한 자동 취소")
    - 결제: 승인 진행 중 → 결제 실패 (실패 사유 `PG_RESPONSE_MISMATCH`)
    - 주문: 7.2에 따라 결제 실패
    - 에러: `502` `PG_RESPONSE_MISMATCH`
    - 메시지: "결제사 응답이 주문 정보와 일치하지 않아 결제를 취소했습니다."
    - 로그: ERROR `[PG 응답 불일치] orderId={주문번호} field={다른 항목} → 승인 취소`
    - 로그: PG 승인 취소마저 실패하면 ERROR `[보상 취소 실패] paymentKey={결제 키} 수동 처리 필요` (결제 실패 처리는 그대로 한다)

19. **PG가 거절하면 결제 실패로 처리한다.**
    - 결제: 승인 진행 중 → 결제 실패 (실패 사유: PG 거절 코드)
    - 주문: 7.2에 따라 결제 실패
    - 에러: `400` `PG_REJECTED` (`pgCode`에 PG 거절 코드)
    - 메시지: PG가 준 거절 사유 그대로

20. **승인 요청이 PG에 닿지 못했으면 다시 결제할 수 있게 되돌린다.**
    - 결제: 승인 진행 중 → 승인 대기 (기록한 결제 키를 지운다)
    - 주문: 7.3에 따라 결제 대기 그대로
    - 에러: `503` `PG_UNAVAILABLE`
    - 메시지: "결제사와 통신할 수 없습니다. 잠시 후 다시 시도해주세요."

21. **PG 결과를 알 수 없으면 결과 확인 중으로 바꾸고, PG에 한 번 조회해 확정을 시도한다.**
    - 결제: 승인 진행 중 → 결과 확인 중
    - 로그: WARN `[결과 불명] orderId={주문번호} → UNKNOWN 전환 후 조회`
    - 조회해서 승인이 확인되고 대조 결과도 맞으면 → 17과 같다
    - 조회해서 결제 실패로 확정되면 (대조 불일치 포함) → `400` `PG_REJECTED`, 메시지는 결제 실패 사유 (없으면 "결제가 승인되지 않았습니다."), `pgCode`는 실패 사유 코드

22. **한 번 조회로도 확정되지 않으면 대사에 맡기고, 결과를 확인 중이라고 응답한다.** PG 조회가 실패했거나 PG에서도 아직 승인 전인 경우다.
    - 결제: 결과 확인 중 그대로
    - 주문: 7.4에 따라 결제 대기 그대로
    - 응답: `202` `PAYMENT_RESULT_UNKNOWN`
    - 메시지: "결제 결과를 확인 중입니다. 잠시 후 결제 내역을 확인해주세요."

23. **PG 요청 중 예상하지 못한 오류가 나면 결과를 알 수 없는 것으로 본다.** 즉시 조회 없이 대사에 맡긴다.
    - 결제: 승인 진행 중 → 결과 확인 중
    - 응답: `202` `PAYMENT_RESULT_UNKNOWN`
    - 메시지: "결제 결과를 확인 중입니다. 잠시 후 결제 내역을 확인해주세요."
    - 로그: ERROR `[예상치 못한 예외] orderId={주문번호}`

##### 항상 지켜야 할 규칙

24. **결과를 알 수 없는 결제는 절대 실패로 단정하지 않는다.** 결과 확인 중으로 두고 PG 조회(즉시 조회 또는 대사)로만 확정한다.
    - 이유: 실제로는 승인되어 돈이 나갔을 수 있다

25. **같은 결제에 대한 PG 승인 요청은 한 번만 나간다.** 동시에 여러 승인 요청이 와도 12를 통과한 하나만 PG에 요청한다.

26. **회원이 금액을 정해 결제를 준비하는 기능은 없다.** 결제는 주문이 접수될 때만 만들어진다.
    - 응답: `404`

### Requirement 7: 결제 결과의 주문 반영

**User Story:** As a 회원, I want to 결제 결과가 주문 상태에 바로 반영되어야, so that 결제 성공·실패를 주문에서 정확히 확인할 수 있다

#### Acceptance Criteria

##### 처리 흐름

1. **결제가 승인되면 주문은 결제 완료가 된다.**
   - 결제: 승인 진행 중 / 결과 확인 중 → 승인 완료
   - 주문: 결제 대기 → 결제 완료

2. **결제가 실패로 확정되면 주문은 결제 실패가 된다.** PG 거절, PG 응답 불일치로 인한 자동 취소, 대사에서 실패 확정이 해당한다.
   - 결제: 승인 진행 중 / 결과 확인 중 → 결제 실패
   - 주문: 결제 대기 → 결제 실패
   - 주문에는 결제의 실패 사유를 그대로 보여준다

3. **승인 요청이 PG에 닿지 못했으면 같은 주문으로 다시 결제할 수 있다.**
   - 결제: 승인 진행 중 → 승인 대기
   - 주문: 결제 대기 그대로

4. **결제 결과를 알 수 없으면 주문은 그대로 둔다.** 대사로 확정될 때까지 기다린다.
   - 결제: 승인 진행 중 → 결과 확인 중
   - 주문: 결제 대기 그대로

5. **이미 실패로 확정된 결제가 PG에서는 승인된 것으로 확인되면 정합성 경보를 남긴다.** 주문 상태는 바꾸지 않는다.
   - 로그: ERROR `[정합성 경보] PG=DONE 인데 DB=FAILED orderId={주문번호}`
   - 이유: 돈은 나갔는데 주문은 실패인 상태 — 운영자 확인 필요

6. **결제 상태가 바뀌었는데 주문이 결제 대기가 아니면 정합성 경보를 남긴다.** 결제 상태 변경은 그대로 둔다.
   - 로그: ERROR `[정합성 경보] 주문 상태 불일치 orderId={주문번호} payment={결제 상태} order={주문 상태}`

##### 항상 지켜야 할 규칙

7. **결제 결과는 어느 경로로 확정되든 같은 방식으로 주문에 반영한다.** 승인 응답, 즉시 확인, 대사 모두 1~6을 똑같이 따른다.
   - 회원에게 주는 응답은 Requirement 6이 정한다. 이 Requirement는 주문 상태 반영만 다룬다 (대사는 회원 응답이 없다)

### Requirement 8: 결제 기한 만료

**User Story:** As a 운영자, I want to 결제 기한이 지난 주문이 자동으로 만료되어야, so that 결제되지 않은 주문이 결제 대기로 계속 남지 않는다

#### Acceptance Criteria

##### 처리 흐름

1. **결제 기한이 지난 주문은 1분마다 자동으로 만료 처리한다.**

2. **만료 대상은 결제가 시작되지 않은 채 결제 기한이 지난 주문이다.**
   - 조건: 주문 결제 대기 + 결제 승인 대기 + 결제 기한 ≤ 현재 시각
   - 경계: 결제 기한 정각도 만료 대상
   - 한 번에 결제 기한이 오래된 순으로 최대 100건

3. **주문이 만료되면 결제도 함께 실패 처리한다.**
   - 결제: 승인 대기 → 결제 실패 (실패 사유 `ORDER_EXPIRED`)
   - 주문: 결제 대기 → 기한 만료

4. **만료와 결제 승인이 겹치면 먼저 확정된 쪽만 반영한다.** 만료를 확정하는 순간 결제가 이미 승인 대기가 아니면(그 사이 승인이 시작됨) 그 주문은 건너뛴다.

5. **한 주문의 만료 처리가 실패해도 나머지 주문은 계속 처리한다.**
   - 로그: ERROR `[만료] 실패 orderId={주문번호}`

##### 항상 지켜야 할 규칙

6. **결제가 진행 중인 주문은 기한이 지나도 만료하지 않는다.** 결제가 승인 진행 중이거나 결과 확인 중인 경우다.
   - 이유: 돈이 나갔을 수 있으므로 대사로 확정한다

7. **여러 서버에서 만료 처리가 동시에 돌아도 주문은 한 번만 만료된다.**

### Requirement 9: 주문·결제 상태 일관성

**User Story:** As a 운영자, I want to 주문 상태와 결제 상태가 항상 맞아야, so that 돈은 나갔는데 주문이 실패로 남는 사고가 생기지 않는다

#### Acceptance Criteria

##### 항상 지켜야 할 규칙

1. **주문 상태와 결제 상태는 항상 다음처럼 짝을 이룬다.**

   | 결제 상태 | 주문 상태 |
   |---|---|
   | 승인 대기, 승인 진행 중, 결과 확인 중 | 결제 대기 |
   | 승인 완료 | 결제 완료 |
   | 결제 실패 | 결제 실패, 주문 취소, 기한 만료 중 하나 |

2. **주문 상태는 결제 상태와 함께 바뀐다.** 한쪽만 바뀐 상태가 외부에 보이지 않는다.

3. **결제 승인 시작, 주문 취소, 기한 만료가 같은 주문에 겹쳐도 하나만 반영된다.**

4. **주문·결제 상태를 바꾸는 동안 외부 시스템(PG, 상품 카탈로그)의 응답을 기다리지 않는다.**
   - 이유: 외부 지연이 주문 처리 전체로 번지지 않도록

5. **주문 상태가 바뀔 때마다 기록을 남긴다.**
   - 로그: INFO `[주문] orderId={주문번호} memberId={회원} {이전 상태}→{다음 상태} reason={사유}`
