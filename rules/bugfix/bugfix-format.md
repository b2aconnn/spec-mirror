# bugfix.md 작성 규칙

bugfix.md는 버그 명세의 1단계 문서입니다. 기능 명세의 requirements.md 자리에 오며, 버그를 **세 가지 동작**으로 나눠 씁니다.

1. **현재 동작 (Defect)**: 지금 무엇이 잘못되는가
2. **기대 동작 (Correct)**: 고친 뒤 무엇이 되어야 하는가
3. **유지할 동작 (Regression Prevention)**: 비슷하지만 버그가 아닌 경우에 **바뀌면 안 되는 것**

세 번째가 핵심입니다. 고칠 범위를 좁히고, 고친 뒤 무엇이 그대로여야 하는지 테스트로 남깁니다.

- 위치: `<specRoot>/<버그 이름>/bugfix.md`. 버그 이름은 영문 소문자·숫자·하이픈입니다. 예: `confirm-recheck-mismatch`
- 기능 명세와 폴더를 나눕니다. 한 폴더에 requirements.md와 bugfix.md를 함께 두지 않습니다.
- 문장은 requirements.md와 같은 **도메인 언어**로 씁니다. 원인, 코드 위치, 고치는 방법은 [bugfix design](design-format.md)에 씁니다.
- 정답 예제: `examples/confirm-recheck-mismatch/bugfix.md`

## 언제 쓰는가

| 상황 | 쓰는 것 |
|---|---|
| 동작이 명세(requirements)와 다르다 | bugfix |
| 명세에 없는 경우에서 잘못 동작한다 | bugfix (기대 동작의 `명세:`를 `새 기준`으로) |
| 원인이 분명하지 않거나, 고친 적이 있는데 다시 깨졌다 | bugfix |
| 오타, 한 줄짜리 명백한 실수 | 명세 없이 바로 고칩니다. 단, 동작이 바뀌면 requirements를 함께 고칩니다 |
| 고치려면 새 기능이 필요하다 | 기능 명세(`/spec-mirror:spec`)를 따로 만들고, bugfix는 원래 결함에만 집중합니다 |

## 형식

~~~markdown
# Bugfix Requirements Document

## Introduction

<어떤 상황에서 무엇이 잘못되는지, 누가 어떤 영향을 받는지 2~5문장>

- 관련 명세: [<기능> requirements](../<기능>/requirements.md) <N.M>
- 범위 밖: <이번에 고치지 않는 것>
- 원인과 고치는 방법은 [design.md](design.md)에 있습니다.

## Bug Analysis

### Current Behavior (Defect)

1.1 **<조건>이면 <잘못된 동작>.**
   - 재현: <어떤 요청·상태에서>
   - 에러: `<상태>` `<에러 코드>`
   - 메시지: "<지금 보이는 문구>"

### Expected Behavior (Correct)

2.1 **<조건>이면 <올바른 동작>.**
   - 에러: `<상태>` `<에러 코드>`
   - 메시지: "<안내 문구>"
   - 명세: <기능> <N.M>

### Unchanged Behavior (Regression Prevention)

3.1 **<비슷하지만 버그가 아닌 조건>이면 지금처럼 <기존 동작>.**
   - 응답: `<상태>` — <응답 내용>
   - 명세: <기능> <N.M>

## Open Questions

없음
~~~

- 섹션은 `Introduction → Bug Analysis → Open Questions` 순서이고, 이 세 개만 씁니다. Open Questions가 없으면 "없음"이라고 씁니다.
- `## Bug Analysis` 아래 제목은 위의 세 `###` 제목만, 이 순서로 씁니다. 더 작은 제목(`####`)은 쓰지 않습니다.

## 항목 규칙

### 번호

- 현재 동작은 `1.1, 1.2, …`, 기대 동작은 `2.1, 2.2, …`, 유지할 동작은 `3.1, 3.2, …`입니다. 각각 1부터 연속입니다.
- **기대 동작은 현재 동작과 같은 수**입니다. `2.N`은 `1.N`을 고친 모습입니다.
- 유지할 동작은 하나 이상입니다. 수는 정해져 있지 않습니다.
- 항목 번호 줄은 `1.1 **…**`처럼 번호, 공백, 굵은 문장입니다. 세부 항목은 세 칸 들여쓴 `   - 이름: 내용`입니다.

### 문장

| 묶음 | 굵은 문장 | 예 |
|---|---|---|
| 현재 동작 | **<조건>이면 <잘못된 동작>.** 관찰된 그대로 씁니다 | **결과를 알 수 없어 PG에 한 번 조회했을 때 승인 내용이 주문과 다르면, PG가 거절한 것처럼 응답한다.** |
| 기대 동작 | **<조건>이면 <올바른 동작>.** requirements 기준처럼 비즈니스 규칙으로 씁니다 | **… 승인 응답에서 불일치가 난 때와 같이 PG 승인을 취소하고 결제 실패로 응답한다.** |
| 유지할 동작 | **<조건>이면 지금처럼 <기존 동작>.** "지금처럼"을 반드시 씁니다 | **승인 응답에서 대조 결과가 다르면 지금처럼 PG 승인을 취소하고 결제 실패로 응답한다.** |

- "지금처럼"은 유지할 동작에만 씁니다.
- 조건은 같은 묶음 안에서도, 세 묶음 사이에서도 **서로 겹치지 않게** 씁니다. 유지할 동작의 조건은 버그 조건과 비슷하지만 버그가 나타나지 않는 경우입니다.
- 결과는 관찰할 수 있게 씁니다: 응답(상태·에러 코드·메시지), 상태 변화, 외부 시스템 요청, 로그.
- requirements의 [문장 규칙](../feature/requirements-format.md#문장-규칙)이 그대로 적용됩니다: 비즈니스 문장, 도메인 언어, 조건은 값으로, 금지 표현.

### 세부 항목

requirements의 항목 이름에 다음 두 개를 더 씁니다.

| 항목 | 쓰는 것 |
|---|---|
| 재현 | 현재 동작에 **필수**. 어떤 요청·상태·데이터에서 나타나는지. 화살표로 순서를 씁니다 (`결제 승인 요청 → PG 결과 불명 → 조회 결과 승인 완료, 15,000원`) |
| 명세 | 기대 동작·유지할 동작에 씁니다. 이 동작을 정한 기능 명세 기준입니다 |

그 밖의 항목 이름(요청 정보, 시점, 조건, 판단, 경계, 에러, 메시지, 응답, 로그, 이유, 예, 형식, 요약)과 `<Glossary 대상>:` 항목은 requirements와 같습니다. 연결된 기능 명세의 Glossary 용어·약어(예: 주문, 결제, PG)를 항목 이름으로 쓸 수 있습니다.

### 명세 연결

`명세:`는 다음 셋 중 하나입니다.

| 쓰는 법 | 뜻 | 테스트 이름 |
|---|---|---|
| `명세: order 6.21` · `명세: order 6.18, 6.21` | 그 기능 명세 기준이 이 동작을 정합니다 | 그 기준의 `R{N}-{M}` (새 테스트는 `R6-21c`처럼 접미사) |
| `명세: 새 기준 (order)` | 지금 명세에 없는 경우입니다. 고치면서 그 기능 명세에 기준을 새로 넣습니다 | 새 기준 번호의 `R{N}-{M}` |
| `명세: 없음` | 이 동작을 다루는 기능 명세가 프로젝트에 없습니다 | `B{N}-{M}` (테스트 파일에 버그 이름을 남깁니다) |

- 기능 명세 기준을 참조할 때는 항상 기능 이름을 붙입니다: `order 7.2`. 숫자만 쓴 `N.M`은 이 문서의 항목입니다.
- 기대 동작이 기능 명세와 다르면, 버그를 고치면서 **기능 명세도 함께 고칩니다**(tasks의 "명세 반영"). 문서에 없는 분기가 코드에 남으면 안 됩니다.
- 기능 명세에 기준을 새로 넣을 때는 [처리 흐름의 순서 정하기](../feature/requirements-format.md#처리-흐름의-순서-정하기)를 따라 **코드에서 그 분기가 들어갈 자리**에 넣습니다. 끝에 덧붙이지 않습니다. 그 뒤 기준 번호가 밀리면 테스트 이름과 코드 주석도 함께 고칩니다([추적 규칙](../traceability.md#기준-번호가-바뀔-때)).

## 쓰기 전에

1. 버그 설명에서 네 가지를 모읍니다: 재현 방법, 지금 결과, 기대 결과, 바뀌면 안 되는 것. 빠진 것은 사용자에게 묻습니다.
2. 관련 기능 명세(requirements)를 읽고, 기대 동작을 정하는 기준을 찾습니다.
3. 코드에서 버그가 나타나는 경로를 따라가며 **비슷하지만 버그가 아닌 경우**를 찾습니다. 이것이 유지할 동작입니다. 같은 분기의 다른 갈래, 같은 결과를 쓰는 다른 경로, 같은 코드를 함께 쓰는 배치가 대표적입니다.

## 작성 후 점검

- [ ] 현재 동작마다 재현 방법이 있고, 그대로 따라 하면 버그가 보인다
- [ ] 기대 동작이 현재 동작과 1:1로 짝을 이룬다
- [ ] 기대 동작의 응답·상태 변화·메시지가 기능 명세와 같거나, 기능 명세를 고칠 내용이 분명하다
- [ ] 유지할 동작이 버그 조건과 가장 가까운 경우들을 덮는다 (같은 분기의 다른 갈래, 같은 코드를 쓰는 다른 경로)
- [ ] 원인·코드 위치·고치는 방법이 bugfix.md에 들어가 있지 않다

## 검사 규칙

| ID | 수준 | 내용 |
|---|---|---|
| BUG000 | 오류 | 채우지 않은 템플릿 자리표시자(`<...>`) |
| BUG001 | 오류 | 첫 줄 `# Bugfix Requirements Document`, 섹션 Introduction → Bug Analysis → Open Questions |
| BUG002 | 오류 | Bug Analysis 아래 세 `###` 제목과 순서, 그 밖의 제목 금지 |
| BUG003 | 오류 | 항목 번호 (묶음 번호와 일치, 1부터 연속), 묶음 밖 항목, 빈 묶음 |
| BUG004 | 오류 | 기대 동작 수 = 현재 동작 수 |
| BUG005 | 오류 | 항목이 `**굵은 문장**`으로 시작 |
| BUG006 | 오류 | 현재 동작에 `재현:` |
| BUG007 | 오류/경고 | 유지할 동작에 "지금처럼" 없음(오류) / 다른 묶음에 "지금처럼"(경고) |
| BUG008 | 경고 | 세부 항목 이름이 허용 목록 밖 |
| BUG009 | 오류 | `에러:` 는 `` `<상태>` `<에러 코드>` `` |
| BUG010 | 경고 | `응답:` 에 `` `<상태>` `` 가 없음 |
| BUG011 | 경고 | `메시지:` 형식, 에러가 있는데 메시지가 없음 |
| BUG012 | 오류 | 금지 표현 |
| BUG013 | 오류 | 기술 용어 |
| BUG014 | 경고 | 코드 식별자처럼 보이는 단어 |
| BUG015 | 오류 | `명세:` 형식, 없는 기능 명세, 없는 기준 |
| BUG016 | 경고 | 기대 동작·유지할 동작에 `명세:` 가 없음 |
| BUG017 | 오류 | 없는 항목 `N.M` 또는 없는 기능 기준 `<기능> N.M` 참조 |

BUG012~BUG014는 Bug Analysis 본문에만 적용하고, 큰따옴표 안의 문구(지금 보이는 메시지 포함)는 검사하지 않습니다.
