# bugfix tasks.md 작성 규칙

버그 명세의 tasks는 **테스트로 버그를 먼저 증명하고, 지금 동작을 기록한 뒤, 고치는** 순서를 고정합니다.

1. 버그 조건 탐색 테스트를 쓰고, **고치기 전 코드에서 실패하는 것**을 확인합니다.
2. 보존 테스트를 쓰고, **고치기 전 코드에서 통과하는 것**을 확인합니다.
3. 고칩니다. 탐색 테스트가 통과하고 보존 테스트가 계속 통과하는지 확인합니다.
4. 기능 명세를 고친 동작에 맞춥니다.
5. Checkpoint

- 위치: `<specRoot>/<버그 이름>/tasks.md`
- 줄 형식, `_Requirements_`, `**Property N: …**`, Dependency Graph는 [기능 tasks 규칙](../feature/tasks-format.md)과 같습니다. 참조 `N.M`은 bugfix.md의 항목입니다.
- 정답 예제: `examples/confirm-recheck-mismatch/tasks.md`

## 형식

~~~markdown
# Implementation Plan: <버그 이름>

## Overview

<무엇을 고치는지 한두 문장>

<진행 방식: 탐색 테스트(실패해야 함) · 보존 테스트(통과해야 함) → 수정 → 확인 → 명세 반영>

## Tasks

- [ ] 1. 버그 조건 탐색 테스트 작성
  - **Property 1: Bug Condition - <design 의 Property 이름 그대로>**
  - **고치기 전 코드에서 실패해야 합니다.** 실패가 버그를 증명합니다. 통과하면 원인 분석이 틀린 것이므로 멈추고 다시 분석합니다
  - 테스트를 고쳐서 통과시키지 않습니다
  - <테스트 이름과 위치>
  - _Requirements: 1.1, 2.1_

- [ ] 2. 보존 테스트 작성 (고치기 전)
  - **Property 2: Preservation - <design 의 Property 이름 그대로>**
  - **고치기 전 코드에서 통과해야 합니다.** 지금 동작을 기록하는 테스트입니다
  - _Requirements: 3.1_

- [ ] 3. 버그 수정: <무엇을 고치는지>
  - [ ] 3.1 <고치는 일>
    - <할 일>
    - _Requirements: 2.1_

  - [ ] 3.2 탐색 테스트 통과 확인
    - **Property 1: Bug Condition - <이름>**
    - 1번의 테스트를 다시 실행합니다. 테스트는 고치지 않습니다
    - _Requirements: 2.1_

  - [ ] 3.3 보존 테스트 통과 확인
    - **Property 2: Preservation - <이름>**
    - _Requirements: 3.1_

- [ ] 4. 명세 반영
  - <기능> requirements.md <N.M> 을 고친 동작에 맞춤 → 사용자 재승인
  - _Requirements: 2.1_

- [ ] 5. Checkpoint - <확인할 범위>
  - 전체 테스트 통과 확인
  - `/spec-mirror:sync <기능>`, `/spec-mirror:sync <버그 이름>`
~~~

## 태스크 규칙

1. **상위 태스크는 다섯 개, 이 순서입니다.** 번호는 1부터입니다. 제목은 아래 말로 시작합니다.

   | 번호 | 제목 | 하는 일 |
   |---|---|---|
   | 1 | `버그 조건 탐색 테스트 작성` | 기대 동작을 담은 테스트. 고치기 전 **실패** 확인 |
   | 2 | `보존 테스트 …` | 유지할 동작 테스트. 고치기 전 **통과** 확인 |
   | 3 | `버그 수정: <무엇을>` | 하위 태스크로 고치는 일 → `탐색 테스트 통과 확인` → `보존 테스트 통과 확인` |
   | 4 | `명세 반영` | 기능 명세(requirements, 필요하면 design)를 고친 동작에 맞춤. 바뀌는 것이 없으면 "변경 없음"을 확인 |
   | 5 | `Checkpoint - …` | 전체 테스트, 명세 동기화 |

   고칠 곳이 여럿이면 3번 아래 하위 태스크를 늘립니다(`3.1`, `3.2`, … 다음에 두 확인 태스크).

2. **Property**
   - 1번에는 design의 모든 Bug Condition Property, 2번에는 모든 Preservation Property를 `**Property N: 이름**`으로 적습니다.
   - 3번의 두 확인 태스크에도 같은 Property를 다시 적습니다.
   - 이 태스크들은 선택(`*`)이 될 수 없습니다. 버그 명세의 Property 테스트는 필수입니다.
3. **참조**: 1번은 현재 동작과 기대 동작(`1.M`, `2.M`), 2번은 유지할 동작(`3.M`)을 참조합니다. bugfix.md의 모든 항목이 어떤 태스크의 `_Requirements_`에 나와야 합니다.
4. **탐색 테스트 결과 기록**: 1번을 마치면 실패 내용·반례를 `  - 결과: …` 한 줄로 남깁니다. 이 줄은 진행 기록이라 tasks 승인을 풀지 않습니다.
5. **Dependency Graph**: 1·2번은 고치는 일보다 **앞 wave**, 두 확인 태스크는 고치는 일보다 **뒤 wave**입니다.

## 탐색 테스트가 고치기 전에 통과하면

원인 분석이 틀렸거나 테스트가 버그 조건을 만들지 못한 것입니다.

1. 멈추고 사용자에게 보고합니다.
2. 테스트가 정말 버그 조건(`isBugCondition`)을 만드는지 확인합니다.
3. 그래도 통과하면 design의 Hypothesized Root Cause로 돌아가 다시 분석하고, design을 고쳐 재승인받습니다.

## 검사 규칙

기능 tasks의 `TSK000`~`TSK010`이 그대로 적용되고, 다음을 더 검사합니다.

| ID | 수준 | 내용 |
|---|---|---|
| BTK001 | 오류 | 상위 태스크 다섯 개의 제목과 순서, 1번부터 시작 |
| BTK002 | 오류 | 탐색·보존 테스트가 선택(`*`)이거나, 해당 종류의 Property를 모두 적지 않음 |
| BTK003 | 오류 | 버그 수정의 하위 태스크 구성 (고치는 일 → 탐색 테스트 통과 확인 → 보존 테스트 통과 확인) |
| BTK004 | 오류 | Dependency Graph에서 테스트 → 수정 → 확인 순서가 아님 |
| BTK005 | 경고 | 완료한 탐색 테스트에 `결과:` 기록이 없음 |
