# requirements.md 작성 규칙

requirements.md는 **비즈니스 규칙의 원본**입니다. 코드를 도메인 언어로 옮긴 것처럼 읽혀야 하고, 코드는 이 문서를 그대로 구현한 것이어야 합니다. 문서와 코드가 다르면 문서가 맞다고 봅니다.

- 위치: `<specRoot>/<기능>/requirements.md` (기본 `docs/spec/<기능>/requirements.md`)
- 구현 정보(API 경로, 코드 구조, 저장소, 기술)는 [design 규칙](design-format.md)에 따라 design에 씁니다.
- 기계 검사 규칙 ID(`REQ001` 등)는 문서 끝 [검사 규칙](#검사-규칙)에 있습니다.

## 형식

```markdown
# 요구사항

## 개요
무엇을 하는 기능인지 2~3문장. 이번에 하지 않는 것과 design.md 링크.

## 용어
- **도메인 용어 (English)**: 정의
- **상태 이름 (Status)**
  - 한글 상태명 (`ENUM_VALUE`): 의미

## 기능별 요구사항

| 🟢 기능 흐름 (요청 · 동작 · 응답) | 🟠 검증 | 🟣 외부 요청 |
|---|---|---|

### 요구사항 N: <기능 이름>

**사용자 이야기:** <누가>는 <무엇을> 하고 싶다. <왜> 위해서다.

#### 인수 조건

##### 처리 흐름

1. 🟢 **회원은 <무엇을> 할 수 있다.**
   - 요청 정보: <회원이 보내는 정보>

2. 🟠 **<지켜야 할 비즈니스 규칙>.** <어기면 어떻게 되는지>.
   - 경계: <허용 값>, <거부 값>
   - 에러: `<상태>` `<에러 코드>`
   - 메시지: "<회원에게 보여줄 안내 문구>"

3. 🟢 **<상태가 바뀌는 규칙>.**
   - 결제: <이전 상태> → <다음 상태> (실패 사유 `<CODE>`)
   - 주문: <이전 상태> → <다음 상태>
   - 이유: <규칙이 필요한 까닭>

4. 🟢 **<결과를 응답한다>.**
   - 응답: `<상태>` — <응답 내용>

##### 항상 지켜야 할 규칙

5. **<흐름의 어느 시점에서든 성립해야 하는 규칙>.**

## 확인이 필요한 사항
확정되지 않은 정책 값과 그 값이 쓰인 기준 번호. "~할까요?"처럼 질문으로 씁니다
```

**한국어 틀과 영어 틀.** 위의 한국어 틀이 기본입니다. 영어 틀도 그대로 받습니다. 한 문서 안에서는 한쪽으로 맞춥니다(REQ021).

| 한국어 틀 | 영어 틀 |
|---|---|
| `# 요구사항` | `# Requirements Document` |
| `## 개요` | `## Introduction` |
| `## 용어` | `## Glossary` |
| `## 기능별 요구사항` | `## Requirements` |
| `### 요구사항 N: <이름>` | `### Requirement N: <이름>` |
| `**사용자 이야기:** <누가>는 <무엇을> 하고 싶다. <왜> 위해서다.` | `**User Story:** As a <역할>, I want to <행동>, so that <가치>` |
| `#### 인수 조건` | `#### Acceptance Criteria` |
| `## 확인이 필요한 사항` | `## Open Questions` |

이 문서의 나머지 부분에서 Introduction · Glossary · Requirements · Open Questions · Acceptance Criteria는 위 표의 같은 섹션을 가리킵니다.

- 섹션은 `개요 → 용어 → 기능별 요구사항 → 확인이 필요한 사항` 순서이고, 이 네 개만 씁니다.
- `## 기능별 요구사항` 바로 아래, 첫 요구사항 앞에 [색 범례 표](#기준-구성-굵은-규칙-한-줄--세부-항목) 한 줄을 둡니다.
- 확인이 필요한 사항이 없으면 섹션을 두고 "없음"이라고 씁니다.

## Glossary 작성 규칙

- **도메인 용어만** 씁니다. 주문, 주문 항목, 결제, 결제 기한, 대사, 각 상태처럼 비즈니스 담당자도 아는 말입니다.
- 클래스·컴포넌트·컨트롤러·테이블은 쓰지 않습니다. 코드 대응은 design의 "도메인 용어 ↔ 코드" 표에 둡니다.
- 용어는 `**한글 용어 (English)**: 정의` 형식입니다. 영문 표기는 코드 이름을 정할 때의 기준이 되므로 되도록 씁니다. 여러 용어를 한 줄에 정의할 때는 `**항목 금액 / 주문 금액**`처럼 `/`로 나눕니다.
- 상태는 `한글 상태명 (ENUM_VALUE)`로 적어 코드 값과 연결합니다.
- 상태 이름은 되도록 겹치지 않게 합니다. 예: 주문 `결제 대기` vs 결제 `승인 대기`
- 상태 묶음 아래에 상태가 아닌 설명 줄(예: "결제 대기 외에는 모두 종결 상태")을 둘 수 있습니다.

## Acceptance Criteria 작성 규칙

기준 하나는 **코드의 분기 하나**이자 **인수 테스트 하나**입니다.

### 구성: 처리 흐름 / 항상 지켜야 할 규칙

Acceptance Criteria는 두 부분으로 나눕니다. 번호는 두 부분에 걸쳐 이어서 매깁니다. 흐름이 1~14면 규칙은 15부터입니다.

**처리 흐름**

요청이 들어와서 응답이 나갈 때까지 코드가 실제로 하는 일을 **실행 순서대로** 씁니다. 위에서 아래로 읽으면 메서드를 위에서 아래로 읽는 것과 같아야 하고, 순서가 다르면 둘 중 하나가 틀린 것입니다.

- 요청 처리 순서: 유스케이스(요청) → 입력 확인 → 조회 → 상태 확인 → 계산 → 생성/변경 → 외부 요청 → 결과별 처리 → 응답
- 배치·이벤트 처리 순서: 시작 조건 → 대상 선정 → 건별 처리 → 실패 처리
- **거절 기준만 나열하지 않습니다.** 처리 흐름에는 반드시 두 가지가 있어야 합니다.
  1. 핵심 동작 (상태 변경, 외부 요청)
  2. 성공을 포함한 **모든 결과의 응답**

  거절 조건만 있고 "그래서 무엇을 하는지"가 없으면 미완성입니다.
- 거절 기준은 위에서부터 확인합니다. 여러 개를 함께 어기면 **처음 어긋난 하나만** 응답하므로, 거절 기준의 순서가 곧 확인 순서입니다.
- 외부 시스템 결과처럼 한 단계에서 여러 갈래로 나뉘면, 그 단계를 한 기준으로 쓰고 갈래마다 기준을 하나씩 둡니다.
  - 예: "PG에 승인을 요청한다. 결과는 승인 / 거절 / 미도달 / 결과 불명 중 하나다"
  - 갈래 순서: **성공 → 확정 실패 → 일시 실패 → 결과 불명 → 예상하지 못한 오류**
  - 코드의 분기 순서가 다르면 코드를 이 순서로 정리합니다.
- 순서를 정하는 기준은 아래 [처리 흐름의 순서 정하기](#처리-흐름의-순서-정하기)에 있습니다.

**항상 지켜야 할 규칙**

흐름의 특정 단계가 아니라, 어느 시점에 확인해도 성립해야 하는 규칙을 씁니다.

- 예: 외부 시스템에 요청하지 않는다, 한번 정해진 값은 바뀌지 않는다, 동시에 요청해도 하나만 반영된다, 본인 것만 보인다, 어느 경로로 오든 같게 처리한다
- 판단 기준: "흐름의 몇 번째 단계 다음에 하는 일인가?"에 답할 수 없으면 규칙입니다.

흐름이 없는 Requirement(예: 상태 일관성)는 `항상 지켜야 할 규칙`만 둡니다.

### 처리 흐름의 순서 정하기

처리 흐름의 순서는 **비즈니스가 실제로 판단하는 순서**이고, 그대로 코드의 분기 순서가 됩니다. 기준을 쓰기 전에 순서부터 정합니다.

**세 가지 원칙**

1. **값싸고 부작용 없는 확인을 먼저 합니다.** 요청만 보고 알 수 있는 것 → 저장된 것을 읽어야 아는 것 → 외부 시스템에 물어야 아는 것 순서입니다. 틀린 요청은 가장 적은 비용으로 돌려보냅니다.
2. **되돌리기 어려운 일은 가장 뒤에 둡니다.** 상태 변경과 외부 요청은 모든 확인을 통과한 뒤에 합니다. 외부 요청 뒤에는 결과 갈래와 응답만 옵니다.
3. **회원이 받는 답이 자연스러운 순서로 둡니다.**
   - 같은 요청을 다시 보낸 회원에게는 거절보다 **기존 결과**를 먼저 돌려줍니다.
   - 존재 여부를 숨겨야 하는 확인(남의 것)은 "없음"과 같은 응답으로 둡니다.

**요청 처리의 확인 순서**

| 순서 | 단계 | 이 단계에서 묻는 것 | 예 (`examples/order`) |
|---|---|---|---|
| 1 | 유스케이스 | 누가 무엇을 요청하는가 (`요청 정보`) | 1.1, 6.1 |
| 2 | 요청 형식 | 필수 값이 있고, 형식·범위가 맞는가 | 1.2 ~ 1.4, 2.1, 6.2 |
| 3 | 같은 요청의 반복 | 이미 받은 요청인가 (중복 방지 키) | 2.2 ~ 2.5 |
| 4 | 대상 | 요청한 대상이 있는가 | 6.3 |
| 5 | 권한 | 본인 것인가 (숨겨야 하면 4와 같은 응답) | 6.4, 3.2, 5.2 |
| 6 | 요청 값 대조 | 요청 값이 저장된 값과 맞는가 | 6.5 |
| 7 | 이미 끝난 같은 요청 | 같은 요청으로 이미 끝났으면 기존 결과를 돌려준다 | 6.6, 5.3 |
| 8 | 상태 | 지금 상태에서 할 수 있는가 (끝남 → 진행 중 → 실패·취소 순) | 6.7 ~ 6.10, 5.4, 5.5 |
| 9 | 시간 | 기한 안인가 | 6.11 |
| 10 | 외부 조회와 계산 | 외부 조회 → 조회 결과로 하는 확인 → 계산 → 한도 | 1.5 ~ 1.10 |
| 11 | 변경 | 만들거나 바꾼다. 확정하는 순간의 경합은 바로 뒤 기준으로 | 1.13, 6.12, 6.13 |
| 12 | 외부 요청 | 외부 시스템에 요청하고, 결과 갈래마다 처리한다 | 6.15 ~ 6.23 |
| 13 | 응답 | 성공 응답 (결과 갈래에 응답이 있으면 그 갈래에) | 1.14, 5.8 |

- 해당하지 않는 단계는 건너뜁니다.
- 비즈니스 이유로 순서를 바꿔야 하면 바꾸고, 앞으로 옮긴 기준에 `이유:`를 씁니다. 예: 기한 확인(9)을 상태 확인(8)보다 먼저 하려면 `이유: 기한이 지난 주문은 상태와 관계없이 새 주문을 안내한다`
- 다른 Requirement의 확인이 흐름 중간에 끼어들면, 끼어드는 자리의 기준에 `시점:`을 씁니다. 예: 1.5 `시점: 위 항목 검증과 중복 주문 확인(Requirement 2)을 통과한 뒤`

**같은 단계 안의 순서**

- **넓은 것에서 좁은 것으로**: 목록 전체(상품 개수) → 항목 하나(수량) → 항목 사이 관계(중복 상품)
- **회원이 고칠 수 있는 것을 먼저**: 형식 오류처럼 회원이 바로 고칠 수 있는 거절이, 상태나 시간처럼 회원이 바꿀 수 없는 거절보다 앞입니다.
- **상태는 끝난 상태부터**: 이미 끝남(같은 요청이면 기존 결과, 다른 요청이면 거절) → 진행 중 → 실패·취소 → 그 밖의 거절 순서입니다. 통과하는 상태(예: 승인 대기)는 마지막에 다음 기준으로 넘어갑니다.

**배치·이벤트 처리의 순서**

시작 조건(주기·계기) → 대상 선정(조건 · 정렬 · 한 번에 처리하는 건수) → 건별 처리(확인 → 변경 → 외부 요청 → 결과) → 건별 실패 처리(다음 건 계속 여부) 순서입니다.

**기존 코드가 있을 때**

기존 기능을 바꾸면 **코드의 실제 순서대로** 씁니다(문장 규칙 11·13). 코드 순서가 이 기준과 다르면 문서를 몰래 바꾸지 않고, Open Questions에 "확인 순서를 바꿀지 (기준 번호)"로 올립니다.

### 코드로 옮기기 좋게 쓰기

처리 흐름을 위에서 아래로 읽으면 코드를 위에서 아래로 읽는 것과 같아야 합니다. 다음처럼 쓰면 기준이 그대로 코드 줄이 됩니다.

| 기준의 모양 | 코드 | 예 |
|---|---|---|
| 🟢 **<역할>은 <무엇을> 할 수 있다.** + `요청 정보` | 진입점과 입력 | 6.1 |
| 🟠 **<규칙>.** <어기면 거절> + `에러` | `if (어김) 거절` 하나 | 6.3 |
| 🟠 **<같은 요청이면> 기존 결과를 돌려준다.** + `응답` | `if (같은 요청) return 기존 결과` | 6.6 |
| 🟣 **<무엇을> 외부 시스템에서 확인한다.** / 🟢 **<무엇을> 계산한다.** | 조회·계산 한 줄 | 1.5, 1.9 |
| 🟢 **<무엇이> <이전> → <다음>으로 바뀐다.** + 대상 항목 | 상태 변경 | 6.12 |
| 🟣 **<외부 시스템>에 요청한다. 결과는 A / B / C 중 하나다.** | 외부 호출 + `when (결과)` | 6.15 |
| 🟢 **<갈래>면 <처리>.** (갈래마다 하나. 바꾸는 것이 없는 외부 결과 갈래면 🟣) | `when`의 갈래 하나 | 6.16 ~ 6.23 |
| 🟢 **<결과>를 응답한다.** + `응답` | `return` | 1.14 |

- **기준 하나에 판단 하나**만 넣습니다. 두 조건을 한 기준에 묶으면 코드에서 분기 하나가 둘로 갈라져 번호를 달 곳이 없어집니다. 같은 응답을 주는 조건 묶음(예: 6.2의 형식 오류들)은 `조건:`에 나열해 한 기준으로 둡니다.
- **확인 · 동작 · 응답을 섞지 않습니다.** "확인하고 바꾸고 응답한다"를 한 기준에 쓰지 않고 세 기준으로 나눕니다.
- **통과한 뒤 하는 일도 기준으로 씁니다.** 계산, 생성, 요청이 빠지면 코드의 본문이 문서에 없게 됩니다.
- 갈래가 나뉘는 곳은 "결과는 … 중 하나다" 기준을 먼저 두고, 갈래 기준을 이어 씁니다.

### 기준 구성: 굵은 규칙 한 줄 + 세부 항목

**처리 흐름의 기준에는 맨 앞에 색을 붙입니다.** 종류 글자는 쓰지 않고 색만 씁니다. 🟢만 따라 읽으면 기능이 무엇을 하는지, 🟠만 따라 읽으면 무엇을 확인하는지 보이고, 🟣에서 외부 시스템을 부릅니다.

| 색 | 굵은 문장이 하는 일 | 주로 붙는 세부 항목 |
|---|---|---|
| 🟢 기능 흐름 | **요청**: 회원이 요청한다 (배치·이벤트면 시작 조건)<br>**동작**: 계산하거나, 발급하거나, 만들거나, 상태를 바꾸거나, 로그를 남긴다<br>**응답**: 회원에게 결과를 돌려준다. 그 밖의 일은 하지 않는다 | `요청 정보`, 상태 변화(`주문:`, `결제:`), `로그`, `응답` |
| 🟠 검증 | 규칙을 확인한다. 어기면 거절하고, 같은 요청이면 기존 결과를 돌려준다 | `경계`, `에러`, `메시지`, 기존 결과면 `응답` |
| 🟣 외부 요청 | 외부 시스템에 묻거나 요청한다 | 외부 시스템 요청(`PG:`) |

```markdown
5. 🟣 **주문 상품의 상품명, 판매가, 판매 여부는 상품 카탈로그에서 확인한다.**
7. 🟠 **존재하지 않는 상품은 주문할 수 없다.**
   - 에러: `400` `PRODUCT_NOT_FOUND`
9. 🟢 **주문 금액은 상품 카탈로그의 판매가로 계산한다.**
```

- 색은 **굵은 문장이 하는 일 하나**로 정합니다. 굵은 문장이 두 가지 일을 하면(예: "바꾸고 응답한다") 기준을 나눕니다.
- **결과 갈래는 그 갈래의 굵은 문장으로 정합니다.** 아무것도 바꾸지 않고 끝나는 외부 결과 갈래(예: 상품 카탈로그 장애로 거절)는 🟣입니다. 상태를 바꾸는 갈래(예: PG 거절 → 결제 실패)는 🟢이고, 그 갈래의 `에러:`·`응답:`은 세부 항목으로 둡니다. 변경하는 순간의 경합(예: 먼저 확정된 쪽만 반영)도 🟢입니다.
- 저장된 값이나 외부 응답을 **대조**하는 기준(예: PG 응답을 주문과 대조)은 🟠입니다.
- 표시는 색 하나이고, 굵은 규칙 앞에 한 칸 띄워 씁니다.
- `항상 지켜야 할 규칙`에는 붙이지 않습니다. 흐름의 단계가 아니라 불변식이기 때문입니다.
- 색의 뜻은 **범례 한 줄**에 둡니다. 아이콘이 처음 나오는 곳 가까이 있도록 `## 기능별 요구사항` 바로 아래, 첫 요구사항 앞에 템플릿의 표를 그대로 씁니다.

  ```markdown
  | 🟢 기능 흐름 (요청 · 동작 · 응답) | 🟠 검증 | 🟣 외부 요청 |
  |---|---|---|
  ```

**근거.** 종류는 Alistair Cockburn, *Writing Effective Use Cases* (Addison-Wesley, 2001)의 분류를 따릅니다. 유스케이스 시나리오의 단계는 ① 행위자 사이의 상호작용(interaction), ② 이해관계자의 이익을 지키는 검증(validation), ③ 이해관계자를 위한 내부 변경(internal change) 셋 중 하나입니다. 여기서 상호작용을 상대에 따라 요청(회원 → 시스템), 외부 요청(시스템 → 외부 시스템), 응답(시스템 → 회원)으로 나눴습니다. 회원과 주고받는 요청 · 응답과 내부 변경(동작)은 함께 🟢 기능 흐름으로, 검증은 🟠, 외부 요청은 🟣로 표시합니다. 처리 흐름과 `항상 지켜야 할 규칙`의 구분은 Bertrand Meyer의 Design by Contract에서 사전조건·사후조건(흐름 안의 검증과 동작)과 불변식(invariant)을 나누는 것과 같습니다.

- 첫 줄은 **굵은 글씨의 비즈니스 규칙**입니다. 기획자가 읽어도 바로 이해되는 문장으로 씁니다.
- 규칙을 어겼을 때의 결과는 같은 줄에 이어서 씁니다. ("~면 주문을 받지 않는다", "~할 수 없다")
- 세부 사항은 아래 들여쓴 항목으로 쓰고, **항목 이름은 다음 중에서만** 고릅니다.

| 항목 | 쓰는 것 |
|---|---|
| 요청 정보 | 회원이 보내는 정보 |
| 시점 | 이 규칙이 흐름 중 언제 적용되는지. 응답 뒤에 따라 일어나는 일이면 지연 허용치(예: `결제 완료 후 5분 안에`) |
| 조건 / 판단 | 규칙이 적용되는 상태 조합, 판단 기준 |
| 경계 | 허용 값과 거부 값 (`20개 가능, 21개 불가`) |
| 에러 | `` `<상태>` `<에러 코드>` `` |
| 메시지 | 회원에게 보여줄 안내 문구 (큰따옴표). 외부 시스템 문구를 그대로 쓰면 `PG가 준 거절 사유 그대로`처럼 출처를 씁니다 |
| 응답 | 거절이 아닌 응답. `` `<상태>` `` — 응답 내용. 코드가 붙는 응답은 `` `202` `<코드>` `` |
| <Glossary 대상> / <외부 시스템> | 상태 변화 `<이전> → <다음>` (실패 사유 포함), 외부 시스템에 보내는 요청. 예: `주문:`, `결제:`, `PG:`. 다른 Requirement가 처리하면 `7.1에 따라 결제 완료`처럼 참조 |
| 로그 | 레벨과 형식 `` ERROR `[정합성 경보] ... orderId={주문번호}` `` |
| 형식 | 시스템이 만드는 값의 모양 (`ORD_` + 26자, 1~64자의 영문·숫자) |
| 요약 | 응답·목록에 담기는 항목 묶음 |
| 이유 | 규칙이 필요한 까닭 한 줄 |
| 예 | 구체적인 예시 |

- `<Glossary 대상>`은 Glossary에 정의한 용어(예: 주문, 결제, 주문 항목)입니다.
- 외부 시스템 이름은 Glossary에 정의했거나 Glossary에 영문 약어로 나오면(예: PG) 항목 이름으로 쓸 수 있습니다. 그 밖의 이름은 설정의 `extraItemLabels`에 넣습니다.
- 이름 없는 들여쓴 줄은 **보충 설명**으로만 씁니다. 예: 계산식(`항목 금액 = 판매가 × 수량`), 갈래별 결과(`조회해서 승인이 확인되면 → 17과 같다`), 덧붙이는 사실(`상품 카탈로그를 조회하지 않는다`)

### 문장 규칙

1. **비즈니스 문장으로 씁니다.** "예외 처리한다", "검증한다" 대신 결과를 말합니다.
   - ❌ "주문 항목이 비어 있거나 20개를 초과하면 예외 처리해야 한다"
   - ✅ "**주문 상품은 1개 이상 20개 이하로 담을 수 있다.** 비어 있거나 20개를 넘으면 주문을 받지 않는다."
   - 규칙은 지켜야 할 모습(긍정형)으로 먼저 쓰고, 어겼을 때 결과를 뒤에 씁니다.
   - 거절 표현: 주문은 "주문을 받지 않는다", 그 외는 "~할 수 없다" / "~하지 않는다"
2. **도메인 언어로 씁니다.** URL, HTTP 메서드, 클래스명, 테이블명, "트랜잭션", "조건부 UPDATE" 같은 기술 용어는 쓰지 않습니다.
   - ❌ "`POST /api/orders`를 요청하면" → ✅ "**회원은 상품과 수량을 골라 주문할 수 있다.**"
   - ❌ "하나의 트랜잭션에서 저장" → ✅ "**주문, 주문 항목, 결제가 함께 만들어진다.** 하나라도 실패하면 아무것도 만들어지지 않는다."
   - ❌ "Conditional_Update가 0행이면" → ✅ "**취소와 결제 승인이 겹치면 먼저 확정된 쪽만 반영한다.**"
   - 어떤 기술로 구현하는지는 design의 구현 규칙에 적습니다.
   - 예외: 상태 코드, 에러 코드, 안내 메시지는 회원에게 보이는 계약이므로 `에러`/`메시지`/`응답` 항목에 씁니다.
   - 동기/비동기, 메시지 큐 같은 처리 방식도 기술입니다. 대신 "응답과 함께 확정되는 것"과 "응답 뒤에 따라 일어나는 것(`시점`에 지연 허용치)"으로 나눠 씁니다. 자세한 기준은 [작업 흐름](../workflow.md#응답-뒤에-따라-일어나는-일)에 있습니다.
3. **첫 기준은 유스케이스입니다.** "회원은 ~할 수 있다" + `요청 정보`. 배치·이벤트형 Requirement는 시작 조건이 첫 기준입니다.
4. **조건은 값으로 씁니다.**
   - ❌ "잘못된 수량이면"
   - ✅ "1개 이상 99개 이하" + `경계: 1개·99개 가능, 0개·100개 불가`
5. **결과는 관찰 가능하게 씁니다.** 해당하는 것을 모두 씁니다: 응답, 상태 변화, 만들어지는지 여부, 외부 시스템 요청 여부, 로그.
6. **처리 흐름의 순서는 코드 실행 순서대로 씁니다.** 순서와 상관없는 규칙은 처리 흐름에 섞지 말고 `항상 지켜야 할 규칙`으로 옮깁니다.
7. **다른 기준 참조**는 다른 Requirement면 `N.M`, 같은 Requirement 안이면 번호만 씁니다. 예: "`(3 이외의 실패 사유)`"
   - 다른 기능 명세의 기준은 기능 이름을 붙입니다: `payment-confirm 6.21에 따라 결제 완료`. 기능을 나누는 기준은 [명세 지도](../spec-map.md)에 있습니다.
8. **금지 표현:** "예외 처리", "적절한", "필요 시", "등을 처리", "에러 응답"(코드·메시지 없이), "실패하면"(어떤 실패인지 없이), "검증해야 한다"(어겼을 때 결과 없이)
9. 정책 수치(한도, 시간, 개수)는 기준 안에 직접 씁니다.
10. 기존 에러 코드를 재사용할 때는 **프로젝트의 에러 코드 정의를 확인해** 기존 메시지를 그대로 씁니다.
11. **기존 기능을 바꾸는 Requirement는 기존 코드를 먼저 읽고 씁니다.**
    - 기존 분기(검증, 거절, 상태 변경, 결과별 응답, 로그)를 하나도 빠짐없이 옮깁니다.
    - 새 분기는 코드에서 들어갈 위치에 끼워 넣습니다.
    - 바뀌는 부분만 쓰면 "코드에만 있는 분기"가 생깁니다.
12. **Requirement끼리 책임을 나눕니다.**
    - 회원에게 주는 응답은 요청을 받는 Requirement에 씁니다.
    - 그 결과로 다른 대상(주문 등)이 따라 바뀌는 것은 별도 Requirement에 씁니다.
    - 같은 내용을 두 곳에 쓰지 말고 `N.M`으로 참조합니다.
13. **기존 코드의 동작이 이상해 보여도 문서에는 실제 동작대로 씁니다.** 바꿀지는 Open Questions에 올립니다. 문서를 쓰면서 동작을 몰래 바꾸지 않습니다.
14. **한국 사람이 읽기 편한 한국어로 씁니다.** 영어를 옮긴 듯한 문장이나 기계가 쓴 듯한 문장을 피합니다.
    - **번역체를 쓰지 않습니다.** "~로 본다", "~하는 것으로 한다", "~에 대해", "~을 가진다"처럼 영어 구문을 옮긴 표현 대신 결과를 바로 씁니다.
      - ❌ "이미 찜한 상품을 다시 담아도 성공으로 본다." → ✅ "이미 찜한 상품은 다시 담지 않는다. 오류 없이 기존 찜을 응답한다."
      - ❌ "결과를 알 수 없는 것으로 본다." → ✅ "결과 불명으로 처리한다."
    - **한 문장에는 하나만** 씁니다. 조건이 여러 개면 굵은 문장은 짧게 쓰고, 조건은 `조건:` 항목으로 내립니다.
      - ❌ "채널과 받기 여부를 모두 보내야 하고, 채널은 … 중 하나, 받기 여부는 … 중 하나여야 한다." → ✅ "채널이나 수신 여부가 없거나 올바르지 않으면 설정을 바꾸지 않는다." + `조건:` 줄
    - **현업과 화면에서 쓰는 말**을 씁니다. 예: "받기 여부 / 받음 · 받지 않음" 대신 "수신 여부 / 켜짐 · 꺼짐", "자기" 대신 "본인의"
    - **번호 참조는 문장 끝에 둡니다.** 문장 가운데에 "8~16을 한다"처럼 번호를 넣지 않고 "차례로 보낸다 (8 ~ 16)"처럼 씁니다. 다른 요구사항의 결과를 가리킬 때는 `7.1에 따라 결제 완료`처럼 씁니다.
    - **사용자 이야기는 "<누가>는 <무엇을> 하고 싶다. <왜> 위해서다."** 두 문장입니다.
    - **확인이 필요한 사항은 질문으로** 끝냅니다. 예: "알림 종류마다 따로 켜고 끌 수 있어야 할까요? (2.1)"

## 작성 후 점검

Requirement 하나를 다 쓰면 다음을 확인합니다.

- [ ] 처리 흐름만 읽어도 "무엇을 하는 기능인지" 알 수 있다 (거절 조건만 있지 않다)
- [ ] 성공했을 때 회원이 받는 응답이 있다
- [ ] 외부 시스템에 요청한다면, 결과 갈래마다 상태 변화와 응답이 있다
- [ ] 기존 기능을 바꿨다면, 기존 코드의 분기가 모두 옮겨져 있다 (에러 코드 목록과 대조)
- [ ] 처리 흐름의 순서가 코드의 실행 순서와 같다
- [ ] 처리 흐름의 순서가 [확인 순서](#처리-흐름의-순서-정하기)를 따른다. 따르지 않는 곳에는 `이유:`가 있거나, 기존 코드 순서라면 Open Questions에 있다
- [ ] 상태 변경과 외부 요청 뒤에는 결과 갈래와 응답만 있다
- [ ] 기준 하나에 판단 하나, 확인 · 동작 · 응답이 섞이지 않았다
- [ ] 처리 흐름의 기준마다 종류가 있고, 굵은 문장이 실제로 하는 일과 맞다
- [ ] 처리 흐름만 위에서 아래로 읽어도 코드의 분기 순서를 그릴 수 있다
- [ ] 순서와 무관한 규칙은 `항상 지켜야 할 규칙`에 있다
- [ ] 다른 Requirement가 다루는 내용은 다시 쓰지 않고 참조했다

`spec-mirror check`가 기계적으로 확인하는 규칙입니다. **오류**는 승인을 막고, **경고**는 리뷰에서 판단합니다.

| ID | 수준 | 내용 |
|---|---|---|
| REQ000 | 오류 | 채우지 않은 템플릿 자리표시자(`<...>`)가 남아 있음 (작성 중에는 훅이 막지 않고 알리기만 합니다) |
| REQ001 | 오류 | 첫 줄 `# Requirements Document`, 네 섹션의 존재와 순서, 그 외 섹션 금지 |
| REQ002 | 오류 | `### Requirement N:` 번호가 1부터 연속 |
| REQ003 | 오류 | `**User Story:** As a …, I want to …, so that …` |
| REQ004 | 오류 | `#### Acceptance Criteria` |
