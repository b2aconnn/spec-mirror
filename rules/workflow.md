# 작업 흐름

명세는 두 종류이고, 둘 다 세 단계를 **순서대로, 단계마다 사용자 승인을 받으며** 진행합니다.

```
기능  requirements ──승인──▶ design ──승인──▶ tasks ──승인──▶ implement ──▶ sync
버그  bugfix       ──승인──▶ design ──승인──▶ tasks ──승인──▶ implement ──▶ sync
        ▲                                                         │
        └──────── 기준(동작)이 바뀌면 항상 첫 단계부터 다시 ───────────┘
```

| | 기능 명세 | 버그 명세 |
|---|---|---|
| 시작 | `/spec-mirror:spec <이름> [설명]` (기존 코드에서 옮기면 `/spec-mirror:adopt`) | `/spec-mirror:bugfix <이름> [버그 설명]` |
| 1단계 | requirements.md — 비즈니스 규칙 | bugfix.md — 현재 동작 / 기대 동작 / 유지할 동작 |
| 2단계 | design.md + design/01~08 | design.md 한 파일 — 원인, 고치는 범위, Property |
| 3단계 | tasks.md — 인수 테스트(Red) → 구현(Green) | tasks.md — 탐색 테스트(실패) · 보존 테스트(통과) → 수정 → 확인 → 명세 반영 |
| 규칙 | `rules/feature/` | `rules/bugfix/` |

## 단계와 승인

| 단계 | 끝나는 조건 |
|---|---|
| 1단계 | 형식 오류 0건 + 사용자 승인 |
| design | 1단계 승인 상태 + 형식 오류 0건 + 사용자 승인 |
| tasks | design 승인 상태 + 형식 오류 0건 + 사용자 승인 |
| implement | 세 단계 모두 승인 상태. 태스크마다 테스트 → 구현 → `R{N}-{M}` 주석 → 체크 |
| sync | 추적표 불일치 0건 + 전체 테스트 통과 |

- 승인 기록은 `<specRoot>/<이름>/.spec-mirror.json`에 문서 해시와 함께 남습니다. 문서에는 아무것도 덧붙이지 않습니다.
- 승인 뒤 문서가 바뀌면 "승인 후 변경됨"이 되고, 다음 단계는 다시 승인될 때까지 잠깁니다.
- 앞 단계가 다시 승인되면 뒤 단계는 "앞 단계가 바뀜"이 됩니다. 뒤 단계 문서를 다시 확인하고, 필요하면 고친 뒤 재승인합니다.
- tasks의 체크 표시(`[ ]`, `[-]`, `[x]`)와 `결과:` 줄은 진행 기록이라 승인을 풀지 않습니다.

### 승인은 사용자만 합니다

- 단계 문서를 다 쓰면 **멈추고** 사용자에게 리뷰를 요청합니다. 스스로 승인하거나 다음 단계로 넘어가지 않습니다.
- 사용자가 대화에서 **분명하게** 승인하면("승인", "좋아, 다음 단계로", "design 진행해") 그때 승인 명령을 실행하고 다음 단계로 갑니다.
- "괜찮아 보이네", "음" 같은 말은 승인이 아닙니다. 애매하면 "승인할까요?"라고 묻습니다.
- 사용자는 `/spec-mirror:approve <이름> [단계]`로 직접 승인할 수도 있습니다.
- 스킬은 승인 명령을 미리 허용하지 않습니다. 대화로 승인받아 실행할 때도 Claude Code의 권한 확인이 한 번 더 뜹니다. 이 확인을 건너뛰도록 설정을 바꾸지 않습니다.

### 훅이 지키는 것

| 훅 | 하는 일 |
|---|---|
| 단계 잠금 (쓰기 전) | 앞 단계가 승인되지 않았으면 다음 단계 문서를 쓰지 못하게 막습니다. 승인 기록(`.spec-mirror.json`)을 직접 고치는 것도 막습니다 |
| 형식 검사 (쓴 뒤) | 명세 문서를 저장할 때마다 검사합니다. 오류가 있으면 그 자리에서 고치게 합니다. 템플릿을 채우는 중(자리표시자가 남음)에는 막지 않고 남은 일만 알립니다 |
| 세션 시작 | 진행 중인 명세와 다음 할 일을 알립니다 |

단계 잠금은 설정 `"stageGate": false`로 끌 수 있습니다(권장하지 않음).

## 리뷰

단계 문서를 다 쓰면 사용자에게 보여 주기 전에 **독립 리뷰**를 받습니다. 모든 단계(기능 · 버그 · adopt의 세 단계, 명세 지도)에 똑같이 적용합니다.

1. **첫 리뷰는 항상 합니다.** `spec-reviewer` 에이전트에 단계, 문서 경로, 규칙 파일의 절대 경로, 관련 코드 경로를 넣어 맡깁니다. 리뷰어는 작성한 대화를 모르고 문서 · 규칙 · 코드만 봅니다.
2. **지적을 직접 확인합니다.** 지적마다 문서와 코드를 다시 보고 맞는 것만 반영합니다. 리뷰 결과를 그대로 믿지 않습니다.
3. **구조가 바뀐 경우에만 다시 리뷰합니다.** 반영하면서 아래 중 하나가 생겼으면, **바뀐 Requirement(버그 명세는 바뀐 묶음, tasks는 바뀐 태스크 묶음)만** 리뷰어에게 한 번 더 맡깁니다. 다시 리뷰는 한 번까지입니다.
   - 기준을 옮기거나, 나누거나, 합쳤다 (확인 순서를 바로잡은 경우 포함)
   - 기준 · 갈래 · 태스크를 새로 넣었다
   - 기준이 다른 Requirement로 옮겨 갔다

   문장이나 세부 항목만 고쳤으면 다시 리뷰하지 않습니다. 형식 문제는 훅이 잡습니다.
4. **리뷰 결과를 보고에 넣습니다.** 사용자가 승인 전에 볼 수 있도록 단계 보고에 다음 표를 넣습니다. 지적이 없었으면 "리뷰 지적 없음"이라고 씁니다.

   | # | 위치 | 지적 | 처리 | 이유 |
   |---|---|---|---|---|
   | 1 | 6.11 | 기한 확인이 상태 확인보다 앞에 있음 | 반영 | 확인 순서 표 8 → 9 |
   | 2 | 1.4 | 1.2와 합치자 | 반영 안 함 | 응답 코드가 달라 분기 2개 |

   다시 리뷰를 했으면 그 결과도 같은 표에 이어서 적습니다. 다시 리뷰 뒤에도 남은 지적은 "사용자 판단"으로 적고 사용자에게 묻습니다.

## 변경 흐름

### 새 기능 / 요구사항 변경
1. requirements를 쓰거나 고칩니다 → 사용자 리뷰·승인
2. design의 영향받는 부분을 고칩니다 → 승인
3. tasks에 바뀐 기준의 태스크를 추가하거나 고칩니다 → 승인
4. 바뀐 기준의 인수 테스트를 먼저 작성·수정하고 실패를 확인합니다 (Red)
5. 테스트를 통과하도록 구현합니다 (Green). 분기에 `R{N}-{M}` 주석을 답니다.
6. 전체 테스트 통과를 확인합니다.

### 버그 수정
1. bugfix.md에 현재 동작 · 기대 동작 · 유지할 동작을 씁니다 → 승인
2. design에 원인(코드를 읽고 확인), 고치는 범위, Property를 씁니다 → 승인
3. tasks를 정해진 다섯 단계로 씁니다 → 승인
4. 탐색 테스트를 쓰고 **고치기 전에 실패**하는지 확인합니다. 통과하면 멈추고 원인을 다시 분석합니다.
5. 보존 테스트를 쓰고 **고치기 전에 통과**하는지 확인합니다.
6. 고칩니다. 탐색 테스트 통과, 보존 테스트 계속 통과를 확인합니다.
7. **기능 명세를 고친 동작에 맞추고 재승인을 받습니다.** 문서에 없는 분기가 코드에 남으면 안 됩니다.

### 급한 수정 (명세 없이 코드를 먼저 고친 경우)
같은 작업 안에서 해당 기능 명세의 기준도 함께 고치고 재승인을 받습니다. 원인이 분명하지 않거나 회귀가 걱정되면 bugfix 명세로 진행합니다.

### 기존 코드에서 명세 만들기
[adopt 규칙](adopt.md)을 따릅니다. 프로젝트 전체면 [명세 지도](spec-map.md)부터 만들고 기능 하나씩 진행합니다. 코드 동작은 바꾸지 않습니다.

### 명세 동기화
[추적 규칙](traceability.md#불일치-처리-명세-동기화)을 따릅니다.

## 응답 뒤에 따라 일어나는 일

메시지 큐, 이벤트, 배치처럼 요청에 대한 응답 뒤에 따로 일어나는 처리는 requirements에서 다음처럼 다룹니다.

- **Requirement를 따로 둡니다.** 회원에게 응답하는 Requirement와 섞지 않습니다.
- 처리 흐름은 이벤트형(시작 조건 → 대상 선정 → 건별 처리 → 실패 처리)입니다.
- `시점`에 지연 허용치를 씁니다. 예: `결제 완료 후 5분 안에`
- 실패 시 다시 시도하는 횟수와, 끝내 실패했을 때 남기는 로그·경보를 씁니다.
- `항상 지켜야 할 규칙`에 다음 두 가지를 씁니다.
  - **누락 허용 여부**: "반드시 보낸다" 또는 "누락될 수 있다"
  - **중복 방지**: 여러 번 받아도 한 번만 반영된다
- "비동기", "메시지 큐", 특정 인프라 이름(예: 메일 발송 서비스)은 쓰지 않습니다. 채널처럼 받는 사람이 겪는 것(예: 이메일)은 씁니다.
- 처리 방식(outbox, 커밋 후 발행 등)은 위의 누락·중복 규칙을 근거로 design에서 고르고, 그 근거를 design에 남깁니다.
