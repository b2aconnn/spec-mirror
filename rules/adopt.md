# 기존 코드에서 명세 만들기 (adopt)

이미 동작하는 코드를 **동작을 바꾸지 않고** 기능 명세로 옮깁니다. 결과물은 일반 기능 명세와 같은 형식(requirements → design → tasks)이고, 그 뒤로는 일반 기능 명세처럼 고치고 관리합니다.

- 명령: `/spec-mirror:adopt <기능> [코드 경로나 설명]`. 기능 없이 부르면 프로젝트 전체의 [명세 지도](spec-map.md)부터 만듭니다.
- 표시: `spec-mirror scaffold <기능> requirements --adopt`가 승인 기록에 `"mode": "adopt"`를 남깁니다. `spec-mirror next`와 `status`가 이 표시를 보여 줍니다.
- 형식은 [기능 명세 규칙](feature/)을 그대로 따릅니다. 이 문서는 **다른 점만** 정합니다.

## 원칙

1. **코드가 하는 일을 그대로 씁니다.** 이상해 보여도 고치지 않고 실제 동작대로 쓰고, 바꿀지는 Open Questions에 올립니다.
2. **분기를 하나도 빠뜨리지 않습니다.** 코드의 분기마다 기준 하나입니다. 분기 목록과 기준을 대조해 빠진 것이 0개여야 합니다.
3. **코드 순서를 따릅니다.** 처리 흐름은 코드의 실제 실행 순서입니다. [확인 순서 표](feature/requirements-format.md#처리-흐름의-순서-정하기)와 다르면 Open Questions에 "확인 순서를 바꿀지 (기준 번호)"로 올립니다.
4. **코드는 바꾸지 않습니다.** adopt의 tasks는 테스트 이름 정리, 빠진 테스트 추가, 분기 주석뿐입니다. 동작을 바꾸는 일은 adopt가 끝난 뒤 `/spec-mirror:spec`(변경)이나 `/spec-mirror:bugfix`로 따로 합니다.

## 1단계: requirements

### 분기 목록 만들기

쓰기 전에 Requirement(진입점)마다 코드를 진입점부터 끝까지 따라가며 분기 목록을 만듭니다. 호출하는 메서드 안까지 들어갑니다.

| # | 위치 | 조건 | 결과 (응답 · 상태 변화 · 외부 요청 · 로그) |
|---|---|---|---|
| 1 | `PaymentStateService.kt:42` | 결제 없음 | `404` `PAYMENT_NOT_FOUND` |
| 2 | `PaymentStateService.kt:45` | 결제의 회원 ≠ 요청 회원 | `403` `FORBIDDEN_PAYMENT` |

- 검증, 거절, 상태 변경, 외부 호출, 결과별 처리, 예외를 잡는 곳, 로그를 모두 적습니다.
- 프레임워크가 하는 확인(요청 형식 검증 등)과 공통 예외 처리도 회원이 받는 응답이 달라지면 적습니다.
- 에러 코드 정의 파일의 코드 목록과 대조해, 이 진입점에서 나올 수 있는 코드가 모두 목록에 있는지 확인합니다.

### 대조

다 쓴 뒤 분기 목록과 기준을 대조합니다. **빈 칸이 0개**여야 합니다.

| 분기 # | 기준 | 비고 |
|---|---|---|
| 1 | 6.3 | |
| 2 | 6.4 | |

- 기준이 없는 분기: 기준을 추가합니다. 일부러 뺐으면 이유를 비고에 씁니다(예: 도달할 수 없는 분기 → Open Questions).
- 분기가 없는 기준: 코드에 없는 동작을 쓴 것입니다. 지웁니다.
- 이 대조표는 단계 보고에 넣어 사용자가 봅니다. design 단계에서는 02의 `### 기준 ↔ 코드 분기`로 옮깁니다.

## 2단계: design

- **지금 구조를 설명합니다.** "추가한다", "새로 만든다", 이름 뒤 `(변경)`을 쓰지 않습니다. Overview 첫 문장은 "본 문서는 <시스템>의 **<기능>**을 코드 그대로 옮긴 기술 설계입니다."처럼 씁니다.
- 코드 조각은 실제 코드에서 가져옵니다. 지어내지 않습니다. 길면 핵심 메서드만 보여 주고 파일 위치를 적습니다.
- 02 Components and Interfaces 끝에 **`### 기준 ↔ 코드 분기`** 표를 둡니다. requirements 단계의 대조표를 코드 위치까지 붙여 옮긴 것입니다.

  | 기준 | 위치 | 분기 |
  |---|---|---|
  | 6.3 | `PaymentStateService.begin` | 결제 조회 결과 없음 |

- 05 Testing Strategy에는 **기존 테스트 → 기준 번호** 이관 표를 둡니다. 예: `AC-CNF-03 → R6-5`
- 08 Deployment · Configuration은 지금 설정을 씁니다. 바뀌는 것이 없으면 "변경 없음 — 기존 설정 그대로"입니다.
- 07의 Property는 지금 코드가 이미 지키는 성질만 씁니다. 지키지 않는 성질을 찾으면 Open Questions(또는 bugfix 후보)로 보고합니다.

## 3단계: tasks

일반 기능 tasks와 형식은 같고, 내용이 **도입 작업**입니다. 템플릿: `templates/adopt/tasks.md` (`scaffold --adopt` 한 명세에 자동으로 쓰입니다)

1. 테스트 지원 코드 확인 (가짜 외부 시스템, 고정 시계, 기준 데이터)
2. Requirement마다
   1. **기존 테스트 정리**: 이름을 `R{N}-{M} <요약>`으로 바꾸고, 검증 내용이 기준과 같은지 확인
   2. **빠진 인수 테스트 추가**: 테스트가 없는 기준. **지금 코드에서 바로 통과해야 합니다**
   3. **코드 주석**: 분기 바로 위에 `R{N}-{M}`, 처리 흐름은 번호 순서대로
3. 최종 Checkpoint: 명세 동기화 불일치 0건, 기존 테스트 전부 통과

### 새 인수 테스트가 실패하면

일반 기능 명세와 반대입니다. adopt에서 새 테스트는 **지금 동작을 기록**하므로 통과해야 합니다. 실패하면 코드를 고치지 않고 멈춥니다.

| 원인 | 처리 |
|---|---|
| 명세가 코드를 잘못 옮김 | requirements를 고치고 재승인 |
| 테스트가 기준을 잘못 검증 | 테스트를 고침 |
| 코드가 틀렸음 (버그) | 명세는 지금 동작대로 두고 Open Questions에 올림. 고치는 것은 adopt가 끝난 뒤 `/spec-mirror:bugfix` |

## 프로젝트 전체를 옮길 때

1. **명세 지도**를 만들고 사용자 승인을 받습니다. 기능 나누기, 순서, Out of Scope를 이때 정합니다. [명세 지도 규칙](spec-map.md)
2. 지도의 순서대로 **기능 하나씩** adopt를 진행합니다. 기능마다 세 단계를 각각 승인합니다.
3. 한 번에 여러 기능을 쓰지 않습니다. 기준이 수백 개가 되면 사람이 리뷰할 수 없고, 넓게 읽으면 분기가 빠집니다.

## 작성 후 점검

- [ ] 분기 목록 ↔ 기준 대조표에 빈 칸이 없다
- [ ] 에러 코드 정의의 코드 중 이 기능에서 나올 수 있는 것이 모두 기준에 있다
- [ ] 처리 흐름이 코드 실행 순서와 같다. 확인 순서 표와 다른 곳은 Open Questions에 있다
- [ ] 이상한 동작을 고쳐 쓰지 않았다 (모두 Open Questions에 있다)
- [ ] design이 지금 구조를 설명하고, 지어낸 코드가 없다
- [ ] tasks에 코드 동작을 바꾸는 일이 없다
