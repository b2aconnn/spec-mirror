# 문서 ↔ 테스트 ↔ 코드 추적 규칙

기준 하나는 **코드 분기 하나**이자 **인수 테스트 하나**입니다. `R{N}-{M}` 번호가 셋을 묶습니다.

`R{N}-{M}`은 requirements의 Requirement N, 기준 M입니다. design·tasks에서는 같은 기준을 `N.M`으로 씁니다.

## 인수 테스트

- **테스트 묶음:** Requirement 하나당 하나입니다. 클래스, 파일, `describe` 블록 등 프로젝트 관례를 따릅니다.
  - 이름에는 기능과 Requirement 이름이 드러나게 합니다.
  - 예: `OrderCancelAcceptanceTest`, `order-cancel.acceptance.test.ts`, `test_order_cancel_acceptance.py`
- **테스트 이름:** `R{N}-{M} <기준 요약>`. 예: `R5-5 결제가 진행 중인 주문은 취소할 수 없다`
  - 기준 하나에 테스트 하나 이상입니다.
  - 경계값은 같은 테스트에서 함께 확인하거나 `R1-2a`, `R1-2b`로 나눕니다.
  - 언어가 테스트 이름에 공백을 허용하지 않으면 표시 이름 기능을 씁니다. 예: `@DisplayName`, `it("R5-5 ...")`, docstring. 그것도 없으면 `test_R5_5_<요약>`처럼 번호를 이름 앞에 둡니다.
- **검증 범위:** 결과로 관찰되는 것을 모두 확인합니다.
  - 응답: 상태, 에러 코드, **메시지까지**
  - 상태 변화, 만들어지는지 여부
  - 외부 시스템 호출 횟수
  - 로그
- **환경:**
  - 진입점부터 저장소까지 실제로 거치는 통합 방식으로 테스트합니다. 프로젝트의 통합 테스트 도구를 씁니다.
  - 외부 시스템은 가짜 구현(fake)으로 바꿉니다.
  - 시간은 고정 시계를 씁니다.
  - 데이터는 design의 테스트 기준 데이터를 씁니다.

## 코드 주석

- 기준을 구현한 분기 **바로 위**에 번호만 답니다. 예: `// R5-5`, `# R5-5`, `-- R5-5`
  - 설명은 문서에 있으므로 반복하지 않습니다.
- **처리 흐름** 기준의 주석은 코드에서도 번호 순서대로 나타나야 합니다. `R1-2`가 `R1-3`보다 위에 있어야 합니다.
  - 흐름이 여러 파일·메서드에 걸치면 호출 순서대로 이어집니다.
- **항상 지켜야 할 규칙**은 특정 분기가 없을 수 있습니다. 그때는 그 규칙을 보장하는 위치에 답니다. 예: 쿼리, 트랜잭션 경계, 유니크 제약, 클래스 주석

## 에러 메시지와 용어

- 에러 코드 정의의 메시지는 기준 문장의 `메시지:`와 **글자까지 같아야** 합니다.
- 새 도메인 용어나 코드 요소가 생기면 design 03의 "도메인 용어 ↔ 코드" 표를 함께 고칩니다.

## 기준 번호가 바뀔 때

처리 흐름 중간에 기준을 넣거나 빼면 뒤 기준의 번호가 밀립니다. 번호는 순서를 나타내므로 끝에 덧붙여 순서를 어기지 않고, 대신 번호를 따라 이름을 고칩니다.

1. requirements의 기준과 그 기준을 가리키는 `N.M` 참조(같은 문서, design, tasks, 버그 명세의 `명세:`)를 함께 고칩니다.
2. 밀린 기준의 테스트 이름 `R{N}-{M}`과 코드 주석을 새 번호로 바꿉니다.
3. `spec-mirror check`와 `spec-mirror trace <이름>`으로 남은 참조와 코드에만 있는 번호가 없는지 확인합니다.

## 버그 명세

버그 명세(bugfix.md)의 기대 동작(2.M)과 유지할 동작(3.M)은 `명세:` 항목으로 기능 명세 기준과 연결됩니다. 테스트와 주석은 그 연결을 따릅니다.

| `명세:` | 테스트 이름 | 코드 주석 |
|---|---|---|
| `order 6.21` | 기능 기준의 번호. 새 테스트는 접미사를 붙입니다: `R6-21c <요약>` | `R6-21` |
| `새 기준 (order)` | 명세 반영 태스크에서 새로 넣은 기준의 번호 `R{N}-{M}` | `R{N}-{M}` |
| `없음` | `B{N}-{M} <요약>` (N.M은 bugfix.md 항목). 테스트 파일에 버그 이름을 주석으로 남깁니다 | `B{N}-{M}` + 같은 파일에 버그 이름 |

- 탐색 테스트는 기대 동작을 담은 테스트입니다. 따로 만들지 않고, 위 이름 규칙대로 기대 동작의 테스트로 씁니다. 고치기 전에 실패하고 고친 뒤 통과합니다.
- 보존 테스트는 유지할 동작의 테스트입니다. 기존 테스트가 이미 있으면 그대로 쓰고, 없으면 추가합니다.
- Property 테스트만 담는 파일(예: `ConfirmRecheckMismatchPropertyTest`)에는 버그 이름을 주석으로 남겨 추적할 수 있게 합니다.
- `spec-mirror trace <버그 이름>`은 기대 동작마다 테스트와 코드 주석을, 유지할 동작마다 테스트를 찾습니다.

## 불일치 처리 (명세 동기화)

`spec-mirror trace <이름>`이 만드는 표로 먼저 보고합니다.

| 기준 | 테스트 | 코드 | 불일치 내용 |
|---|---|---|---|

| 불일치 | 처리 |
|---|---|
| 문서에만 있음 | 테스트 → 코드 순으로 추가 |
| 코드에만 있음 (문서에 없는 분기·번호) | 문서에 추가할지 코드에서 지울지 **사용자에게 묻습니다** |
| 둘 다 있으나 다름 (에러 코드, 메시지, 상태, 순서) | 문서 기준으로 테스트 → 코드 순서로 고침 |
| 처리 흐름 주석 순서가 문서 번호와 다름 | 코드 분기 순서를 문서대로 정리 (동작이 바뀌면 사용자에게 묻습니다) |

- 문서와 코드가 다르면 **문서가 맞다**고 봅니다.
- 단, 코드 쪽이 의도된 것으로 보이면 고치기 전에 사용자에게 묻습니다.
- 코드를 먼저 고쳐야 했던 경우(버그 수정 등)에는 같은 작업 안에서 requirements의 해당 기준도 함께 고칩니다. 문서에 없는 분기가 코드에 남으면 안 됩니다.
