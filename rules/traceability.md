# 문서 ↔ 테스트 ↔ 코드 추적 규칙

기준 하나는 **코드 분기 하나**이자 **테스트 시나리오 하나 이상**입니다. `R{N}-{M}` 번호가 셋을 묶습니다.

`R{N}-{M}`은 requirements의 Requirement N, 기준 M입니다. design·tasks에서는 같은 기준을 `N.M`으로 씁니다.

## 테스트

기준을 검증하는 테스트는 **BDD 형식의 시나리오**로 씁니다. 테스트가 확인하는 것은 코드의 동작이 아니라 **도메인 정책**입니다.

### 쓰는 원칙

1. **시나리오에 집중합니다.** 테스트 하나는 시나리오 하나입니다. 상황(given) · 행동(when) · 결과(then)로 씁니다.
2. **개발자가 아니어도 읽을 수 있게 씁니다.** 테스트 이름과 given / when / then은 requirements의 도메인 용어로 씁니다. 응답 코드, 에러 코드, 영문 상태 값, API 경로, 클래스 · 메서드 이름을 쓰지 않습니다.
3. **현상이 아니라 정책을 씁니다.** 응답 · 메시지 · 상태 값 · 호출 횟수 · 로그처럼 테스트가 관찰하는 것을 쓰지 않고, 그 관찰이 뜻하는 정책을 씁니다.

| 현상 (쓰지 않음) | 정책 (씀) |
|---|---|
| 결제 기한 정각에 승인을 요청하면 `400` `PAYMENT_EXPIRED`를 응답한다 | 결제 기한이 되면 결제할 수 없다 |
| 결제사 승인 요청이 한 번만 호출된다 | 같은 주문을 동시에 여러 번 결제해도 결제는 한 번만 이루어진다 |
| 결제 상태가 `FAILED`, 주문 상태가 `PAYMENT_FAILED`가 된다 | 주문은 결제 실패가 된다 |

### 어느 테스트가 맡는지

기준은 **그 판단을 하는 코드를 확인하는 테스트**가 맡습니다. 판단 위치는 design 02에 있고, 기준마다 어떤 테스트가 맡는지는 design 05의 `기준 ↔ 테스트` 표에 씁니다.

- 테스트 종류(예: 유닛 · 통합 · E2E)와 각각 무엇을 확인하는지, 거절을 예외로 볼지 응답으로 볼지는 **convention**을 따릅니다([convention 규칙](convention.md)).
- 여러 테스트에서 같은 기준을 함께 확인해도 됩니다. 그 테스트도 같은 `R{N}-{M}` 이름을 씁니다.
- 기존 코드(adopt, 기존 기능 변경)는 지금 코드에서 판단하는 곳을 따릅니다. 테스트를 위해 코드를 옮기지 않습니다.

### 회원이 받는 응답

- **design 04의 에러마다 회원이 실제로 받는 응답(응답 코드 · 에러 코드 · 메시지)을 확인하는 시나리오가 하나 이상** 있어야 합니다. 기준을 다른 테스트가 맡아도, 회원에게 어떻게 전달되는지는 대표 시나리오로 확인합니다. 어느 시나리오가 확인하는지는 design 05의 `에러 ↔ 응답 테스트` 표에 씁니다.
- 메시지는 어느 테스트에서 확인하든 requirements와 글자까지 같아야 합니다.

### 테스트 이름

`R{N}-{M} <상황>이면 <결과>다`

- 테스트 이름만 봐도 상황과 결과를 알 수 있게 씁니다. 기준 문장이 앞 기준에 기대면("대조 결과가 맞으면") 그 상황을 풀어 씁니다.
  - 기준 6.17 "대조 결과가 맞으면 결제를 승인 완료로 바꾼다" → `R6-17 결제사가 주문과 같은 내용으로 승인하면 결제가 완료된다`
- 문장으로 끝냅니다(`~다`). `~불가`, `~성공`처럼 명사로 끝내지 않습니다.
- 유스케이스와 항상 지켜야 할 규칙은 `<누가>는 <무엇>을 할 수 있다`, `<상황>이어도 <결과>다`로 씁니다.
  - 예: `R6-25 같은 주문을 동시에 여러 번 결제해도 결제는 한 번만 이루어진다`
- 다른 테스트가 맡은 기준이 회원에게 전달되는지 확인할 때는 결과를 "안내받는다"로 씁니다.
  - 예: `R6-5 회원이 주문 금액과 다른 금액으로 결제하면 결제할 수 없다고 안내받는다`
- 언어가 테스트 이름에 공백을 허용하지 않으면 표시 이름 기능을 씁니다. 예: `@DisplayName`, `it("R5-5 ...")`, docstring. 그것도 없으면 `test_R5_5_<요약>`처럼 번호를 이름 앞에 둡니다.

### 결과 하나에 시나리오 하나

- **결과가 다르면 시나리오를 나눕니다.** 기준 하나가 여러 결과를 가지면 `R1-2a`, `R1-2b`처럼 접미사를 붙입니다.
- **결과가 같으면 한 시나리오의 예시로 묶습니다.** 경계값이나 같은 결과를 내는 여러 조건은 파라미터 테스트(Gherkin의 시나리오 개요 + 예)로 씁니다.
- requirements `경계:`의 값은 모두 예시에 들어가야 합니다. 범위에 양쪽 끝이 있으면 양쪽 모두입니다.

```
R1-2a 주문 상품이 1개 이상 20개 이하면 주문할 수 있다      예: 1개, 20개
R1-2b 주문 상품이 없거나 20개를 넘으면 주문할 수 없다      예: 0개, 21개
```

### 본문

- `// given` → `// when` → `// then` 주석으로 나눕니다. 이어지는 조건과 결과는 `// and`로 씁니다. 주석도 도메인 용어로 씁니다.
- **when은 하나**입니다. 행동이 둘이면 시나리오를 나눕니다. 예외를 확인할 때는 when과 then이 한 줄로 붙어도 됩니다(`// when …하면` + `// then …거절된다`).
- **현상 확인은 테스트 지원 코드가 맡습니다.** 시나리오 본문에는 `결제가_완료된다()`, `거절된다(결제_거절_사유.결제_기한_만료)`처럼 정책을 부르고, 응답 코드 · 에러 코드 · 메시지 · 상태 값 · 호출 횟수 · 로그 확인은 그 안에서 합니다.
- 테스트 지원 코드의 이름도 도메인 용어로 씁니다(한글이든 영어든 프로젝트 관례). 회원이 받는 안내 · 거절 사유는 requirements의 에러 코드 · 메시지와 1:1인 목록 하나로 둡니다.
- 확인하는 것은 줄이지 않습니다. 결과로 관찰되는 것(응답 · 에러 코드 · **메시지까지** · 상태 변화 · 만들어지는지 여부 · 외부 시스템 호출 횟수 · 로그)을 그 테스트가 볼 수 있는 만큼 모두 확인합니다.

```kotlin
@ParameterizedTest(name = "기한 {0}")
@ValueSource(strings = ["정각", "1초 후"])
fun `R6-11b 결제 기한이 되면 결제를 시작할 수 없다`(시점: String) {
    // given 결제 기한이 01:30인 결제가 승인을 기다리고 있다
    val 결제 = 승인_대기_결제(결제_기한 = "01:30")

    // when 결제 기한 <시점>에 결제를 시작하면
    // then 결제 기한이 지났다는 이유로 거절된다
    거절된다(결제_거절_사유.결제_기한_만료) {
        결제.승인을_시작한다(시각 = 결제_기한_기준(시점))
    }

    // and 결제는 승인 대기 그대로다
    결제.승인_대기_그대로다()
}
```

### 테스트 묶음과 환경

- **테스트 묶음:** 클래스, 파일, `describe` 블록 등 convention을 따릅니다. 정해진 것이 없으면 테스트 종류마다 Requirement 하나당 하나를 기본으로 합니다.
- 외부 시스템은 가짜 구현(fake)으로 바꿉니다.
- 시간은 고정 시계를 씁니다.
- 데이터는 design 05의 테스트 기준 데이터를 씁니다.

## 코드 주석

- 기준을 구현한 분기 **바로 위**에 번호만 답니다. 예: `// R5-5`, `# R5-5`, `-- R5-5`
  - 설명은 문서에 있으므로 반복하지 않습니다.
- **처리 흐름** 기준의 주석은 코드에서도 번호 순서대로 나타나야 합니다. `R1-2`가 `R1-3`보다 위에 있어야 합니다.
  - 흐름이 여러 파일·메서드에 걸치면 호출 순서대로 이어집니다.
- **항상 지켜야 할 규칙**은 특정 분기가 없을 수 있습니다. 그때는 그 규칙을 보장하는 위치에 답니다. 예: 쿼리, 트랜잭션 경계, 유니크 제약, 클래스 주석

## 에러 메시지와 용어

- 에러 코드 정의의 메시지는 기준 문장의 `메시지:`와 **글자까지 같아야** 합니다.
- 코드의 이름은 design 03의 "도메인 용어 ↔ 코드" 표를 따릅니다. 이름 짓는 법은 [design 규칙의 이름 짓기](feature/design-format.md#이름-짓기)에 있습니다.
- 새 도메인 용어나 코드 요소가 생기면 design 03의 "도메인 용어 ↔ 코드" 표를 함께 고칩니다. Glossary에 없는 도메인 개념이면 코드에서 이름을 지어내지 않고 requirements 보완부터 합니다.
- Glossary의 상태 값(`ENUM`)은 코드의 상태 값과 같아야 합니다. `spec-mirror trace`가 코드에서 찾지 못한 상태 값을 알려 줍니다.

## 기준 번호가 바뀔 때

처리 흐름 중간에 기준을 넣거나 빼면 뒤 기준의 번호가 밀립니다. 번호는 순서를 나타내므로 끝에 덧붙여 순서를 어기지 않고, 대신 번호를 따라 이름을 고칩니다.

1. requirements의 기준과 그 기준을 가리키는 `N.M` 참조(같은 문서, design, tasks, 버그 명세의 `명세:`)를 함께 고칩니다.
2. 밀린 기준의 테스트 이름 `R{N}-{M}`과 코드 주석을 새 번호로 바꿉니다.
3. `spec-mirror check`와 `spec-mirror trace <이름>`으로 남은 참조와 코드에만 있는 번호가 없는지 확인합니다.

## 버그 명세

버그 명세(bugfix.md)의 기대 동작(2.M)과 유지할 동작(3.M)은 `명세:` 항목으로 기능 명세 기준과 연결됩니다. 테스트와 주석은 그 연결을 따릅니다.

| `명세:` | 테스트 이름 | 코드 주석 |
|---|---|---|
| `order 6.21` | 기능 기준의 번호. 새 테스트는 접미사를 붙입니다: `R6-21c <상황>이면 <결과>다` | `R6-21` |
| `새 기준 (order)` | 명세 반영 태스크에서 새로 넣은 기준의 번호 `R{N}-{M}` | `R{N}-{M}` |
| `없음` | `B{N}-{M} <상황>이면 <결과>다` (N.M은 bugfix.md 항목). 테스트 파일에 버그 이름을 주석으로 남깁니다 | `B{N}-{M}` + 같은 파일에 버그 이름 |

- 버그 명세의 테스트도 [테스트](#테스트)의 BDD 형식을 따릅니다. 이름의 `<요약>`은 `<상황>이면 <결과>다`로 쓰고, 버그를 고치는 코드를 확인하는 테스트(종류는 convention)로 씁니다.
  - 예: `R6-21c 결제사에 다시 조회한 승인 내용이 주문과 다르면 그 결제는 취소되고 실패한다`
- 탐색 테스트는 기대 동작을 담은 테스트입니다. 따로 만들지 않고, 위 이름 규칙대로 기대 동작의 테스트로 씁니다. 고치기 전에 실패하고 고친 뒤 통과합니다.
- 보존 테스트는 유지할 동작의 테스트입니다. 기존 테스트가 이미 있으면 그대로 쓰고, 없으면 추가합니다.
- Property 테스트만 담는 파일(예: `ConfirmRecheckMismatchPropertyTest`)에는 버그 이름을 주석으로 남겨 추적할 수 있게 합니다.
- `spec-mirror trace <버그 이름>`은 기대 동작마다 테스트와 코드 주석을, 유지할 동작마다 테스트를 찾습니다.

## 불일치 처리 (명세 동기화)

`spec-mirror trace <이름>`이 만드는 표로 먼저 보고합니다.

| 기준 | 테스트 | 코드 | 불일치 내용 |
|---|---|---|---|

| 불일치 | 처리 |
|---|---|
| 문서에만 있음 | 테스트 → 코드 순으로 추가 |
| 코드에만 있음 (문서에 없는 분기·번호) | 문서에 추가할지 코드에서 지울지 **사용자에게 묻습니다** |
| 둘 다 있으나 다름 (에러 코드, 메시지, 상태, 순서) | 문서 기준으로 테스트 → 코드 순서로 고침 |
| 처리 흐름 주석 순서가 문서 번호와 다름 | 코드 분기 순서를 문서대로 정리 (동작이 바뀌면 사용자에게 묻습니다) |

- 문서와 코드가 다르면 **문서가 맞다**고 봅니다.
- 단, 코드 쪽이 의도된 것으로 보이면 고치기 전에 사용자에게 묻습니다.
- 코드를 먼저 고쳐야 했던 경우(버그 수정 등)에는 같은 작업 안에서 requirements의 해당 기준도 함께 고칩니다. 문서에 없는 분기가 코드에 남으면 안 됩니다.
